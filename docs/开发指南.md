## 一、环境准备

| 组件 | 版本要求 | 说明 |
|---|---|---|
| Node.js | 24 | 与主仓库 `CopperCore/.github/workflows/` 的 CI 一致 |
| Rust | stable | 经 `dtolnay/rust-toolchain@stable` 安装，与主仓库一致 |

本仓库沿用 `CopperCore/` 的既有构建方式（`frontend/` 放 Vue 包、`src-tauri/` 放 Rust crate），便于在两个仓库之间迁移认知。

## 二、五分钟跑起来

```
git clone <本仓库地址>
cd cgl-models
npm install
npm run dev
```

`npm run dev` 启动 Vite 开发服务器（`vite --config vite.config.ts`，端口 1520，`strictPort`），宿主页为 `frontend/index.html`（加载 `frontend/src/dev-preview.ts` 这个最小 Vue 宿主），用于独立预览模块页面。此步已实测通过。

**阶段一的重要前提**：内核当前只支持静态编译的内置模块。前端包要在启动器里真正生效，必须被内核 `CopperCore/frontend/src/modules/index.ts` 静态 `import`；`npm run dev` 只能验证模块页面自身，不能把它送进启动器。这一点见 [设计](设计.md) 的「现状差距」。

后端侧单独构建与测试：

```
npm run build:backend
cargo test --manifest-path src-tauri/Cargo.toml
```

> **状态更新（已实测通过）**：此前标记的 G14（内核 crate 未开放模块可见性）与 G15（缺 OpenSSL 开发环境）两处前置阻塞**均已解除**——内核侧 `CopperCore/src-tauri/src/lib.rs` 已开放 `pub mod registry / pub mod services / pub mod error / pub mod state`，且本仓库可经 `CopperCore/.cargo/env-check.ps1` 配置 OpenSSL 环境后完成链接。`cargo test --manifest-path src-tauri/Cargo.toml` 当前 35 项全部通过。

## 三、改哪几个文件

模板骨架里，改这五个文件就能完成一次完整的模块开发。

| 文件 | 作用 | 改动时机 |
|---|---|---|
| `module.json` | 模块清单（唯一数据源）：id、i18n_namespace、名称、版本、平台、权限、入口 | 每次身份或元信息变化 |
| `frontend/src/register.ts` | 前端注册入口：`registerModule({ id, nav, routes })` | 改导航、路由、图标时 |
| `src-tauri/src/module.rs` | `Module` trait 实现：`id` / `init` / `start` / `stop` | 改生命周期、事件订阅、意图声明时 |
| `src-tauri/src/commands.rs` | 模块 Tauri 命令：薄封装，参数校验 + 调 service | 需要新的前后端通路时 |
| `frontend/src/locales/*.json` | 语言包（扁平键，`zh-CN` 与 `en-US` 键集必须一致） | 任何时候新增文案 |

配套文件（按需改）：

| 文件 | 作用 |
|---|---|
| `src-tauri/src/service.rs` | 业务逻辑，与命令层解耦，便于单测 |
| `src-tauri/src/storage.rs` | 持久化：`migrate_scope` 迁移 + 读写访问器 |
| `src-tauri/src/intents.rs` | 意图声明与处理（模块对外提供的能力） |
| `src-tauri/src/manifest.rs` | `module.json` 的反序列化结构（与 `module.schema.json` 对齐） |
| `src-tauri/build.rs` | 构建期把 `module.json` 注入为编译期常量 |
| `frontend/src/api.ts` | 模块命令类型化封装（禁止裸调 `invoke`） |
| `frontend/src/events.ts` | 模块订阅的内核事件类型化封装 |
| `frontend/src/composables/useModuleState.ts` | 模块前端状态（单例 + 事件驱动） |
| `frontend/src/ModulePage.vue` / `ModuleDetail.vue` | 列表页与详情页 |
| `frontend/src/components/ModuleListRow.vue` / `ModuleEmptyState.vue` | 列表行与空状态（消费主题令牌，图标用 `@lucide/vue` 图标名） |
| `frontend/src/styles/module.css` | 模块私有样式，只消费 `var(--copper-*)` |

**命名纪律**：文件名写该文件的作用，不体现执行顺序。不要出现 `step1_init.rs`、`01_build.yml` 这类命名。

```rust
// 语言包注册（第一个参数必须是 i18n_namespace，不是完整 id）
```

```rust
// 事件：订阅 / 发布 / 退订
let sub = kernel.events().subscribe("download.status", |name, payload| { /* 至少一次 */ });
kernel.events().publish("demo-tools.activity", payload);
kernel.events().unsubscribe(sub);   // 在 stop 中调用
```

```rust
// 意图：声明 / 发起 / 注销
kernel.intents().declare("demo-tools.echo", MODULE_ID, handler)?;   // 重复声明报错
let out = kernel.intents().request("expose.version", serde_json::json!({}))?;
```

```ts
// 事件订阅（后端 `download.status` -> 前端 `download-status`）
import { listen } from "@tauri-apps/api/event";

```

### 前端约定速查

| 项 | 要求 |
|---|---|
| 主题令牌 | 只用 `var(--copper-*)`（颜色 / 圆角 / 间距 / 尺寸 / 动效），禁止颜色字面量 |
| 图标 | 只用 `@lucide/vue` 图标组件，禁止 emoji |
| 通信 | 禁止裸调 `invoke`，一律经 `api/core.ts` 的 `call` 或模块 `api.ts` 封装 |

| 性能 | 长列表虚拟滚动；进度类事件节流，避免高频重渲染 |
| 页面级操作按钮 | 经 `#copper-titlebar-actions` Teleport 锚点注入标题栏 |

## 五、两个联动范例

### 范例一：订阅内核事件 `download.status`

场景：模块要在下载完成时做一次本地记录更新。

后端（`src-tauri/src/module.rs` 的 `init`）：订阅内核全局下载事件，在 `stop` 中退订。

```rust
let sub = kernel.events().subscribe("download.status", move |_name, payload| {
    // 负载为 DownloadTaskView 序列化结果（snake_case）：id / status / total_bytes / downloaded_bytes / error ...
    let Some(task_id) = payload.get("id").and_then(serde_json::Value::as_u64) else { return };
    match payload.get("status").and_then(serde_json::Value::as_str) {
        Some("done") => { /* 更新本地记录为已完成 */ }
        Some("failed") | Some("cancelled") => { /* 落失败态 */ }
        _ => {}
    }
});
```

要点：

1. **至少一次语义**——订阅时会补发重放缓冲内匹配的历史事件，所以处理逻辑必须幂等（上面按 `task_id` 更新是天然幂等的写法）。
2. **回调是同步的**——重活经 `kernel.runtime().spawn(...)` 派生。
3. **必须在 `stop` 中 `unsubscribe`**，否则模块关闭后仍被事件总线持有。
4. 内核侧真实样例可对照 `CopperCore/src-tauri/src/modules/game_download/mod.rs` 与 `modules/content_download/mod.rs` 的 `download.status` 处理。

同一个事件在前端的事件名是 `download-status`（`.` → `-`）。本模板 `frontend/src/events.ts` 的 `onKernelDownloadStatus` 即此封装的现成实现。

### 范例二：发起意图 `expose.version`

场景：模块要拿到当前游戏版本清单，但版本扫描属于开始页模块的职责。模块之间不互相依赖，所以走意图。

后端：

```rust
let list = kernel.intents().request("expose.version", serde_json::json!({}))?;
// 返回：数组，元素形如 { "name": ..., "game_version": ..., "type": ..., "registered": ... }
```

要点：

1. `expose.version` 由 `home` 模块声明（`CopperCore/src-tauri/src/modules/home/mod.rs:240`），负载忽略，返回版本对象数组。
2. **未声明时 `request` 返回错误**（错误文本含「无模块声明」）。模块应把这种情况当作可降级的能力缺失来处理，而不是崩溃。
3. 意图处理者是**同步**的，模块自己的意图若涉及重活，应在处理者内 `tokio::spawn`。
4. 声明意图时：**同一意图重复声明直接报错**（不静默覆盖），所以意图名要带模块域前缀避免撞名。
5. 模块停止时用 `kernel.intents().withdraw(MODULE_ID)` 注销自己声明的全部意图。

本模板的示例模块经命令 `demo_tools_expose_version` 暴露该能力（`frontend/src/api.ts` 的 `demoExposeVersion`），用于演示跨模块意图链路。

## 六、调试

### 同步进启动器模块目录

```
npm run import:dev
npm run import:dev:watch
```

`scripts/import-dev-module.mjs` 的行为：解析 `module.json` → 构建前端与后端 → 目标目录 `<modules_dir>/<id>/` → 原子替换 `backend/` 与 `frontend/` → 写 `dev.json` → 打印「请在启动器设置 → 模块 中启用并重启加载」。

目录约定（内核已存在 `Paths::modules_dir()`，Windows 下为 `%APPDATA%\copper-lamp\copper-golem\modules`）：

```
<modules_dir>/
└─ copper-lamp.demo-tools/
   ├─ module.json      清单
   ├─ backend/         后端产物
   ├─ frontend/        前端产物（register.js + assets）
   └─ dev.json         开发模式标记（仅本地调试，不入发布包）
```

**脚本本身不调用内核命令**，而是直接写文件系统——这是有意的：内核侧的 `modules_import_local` 等导入命令**尚未实现**，且模块目录不可写或内核未启动时不应让脚本失败。

### 日志

内核日志由 `tauri-plugin-log` 统一写出，日志目录为 `Paths::logs_dir()`。`modules_dev_log`（按模块 id 拉取最近日志）**尚未实现**，当前只能直接查看日志目录下的文件。

### 常见「没反应」排查表

| 症状 | 最可能的原因 | 核对方法 |
|---|---|---|
| 左导航没有入口 | `register.ts` 未被内核引入 | 阶段一必须由 `CopperCore/frontend/src/modules/index.ts` 静态 `import` 本模块的 `register.ts` |
| 点进去空白 | `nav.path` 与 `routes[].path` 不一致 | 两者逐字相同 |
| 文案显示键名 | 语言包未注册，或键前缀用了完整 `id` | 后端 `register_module_pack` 传 `i18n_namespace`；前端键为 `module.demo-tools.<扁平键>` |
| 部分文案回退英文或键名 | `zh-CN` / `en-US` 键集不一致 | `npm run schema:check` |
| 模块整体不可见 | 模块未注册 | `id()` 必须与 `module.json.id` 逐字一致 |
| 状态 `failed` | `init` 或 `start` 返回 `Err` | 错误文本经 `modules_list` 暴露在设置页模块 Tab |
| 改了代码没变化 | 模块被停用 | 设置键 `modules.<id>.enabled`；切换后**下次启动生效** |
| 命令报「命令未找到」 | 命令未进 `generate_handler![...]` | 本仓库 `frontend/src/api.ts` 会归一化为 `not_registered`；阶段一需把命令加入内核静态列表 |
| 事件收不到 | 前端监听名没把 `.` 换成 `-` | 后端 `download.status` → 前端 `download-status` |
| 事件重复触发 | 事件总线是至少一次语义 | 处理逻辑做幂等 / 去重（本模板 `useModuleState.ts` 按 `kind + at + message` 去重） |
| 表不存在 | 迁移未执行，或表名留了点号 | `init` 中调 `migrate_scope`；表名把 `.` 与 `-` 换成 `_` |
| `error[E0603]: module ... is private` | 内核 crate 该模块未开放可见性 | 已确认内核开放了模块侧所需的 `registry` / `services` / `error` / `state`；若仍报私有多为主仓库当前分支缺补丁，需同步最新内核 |
| 链接期报找不到 OpenSSL | 内核依赖链需要 OpenSSL | 用 `CopperCore/.cargo/env-check.ps1` 配置 `OPENSSL_DIR` 等方式后再构建（详见该脚本注释） |

`is_builtin` 相关的历史误导已消除：`ModuleInfo.is_builtin` 此前恒为 `true`（硬编码），现已由 `ModuleOrigin`（`Builtin` / `Addon`）提供真实值，`list()` 同时返回 `suspended`。若看到旧资料称该字段恒为 `true`，属过期信息。

**另有两条此前不属于「没反应」但会让开发直接卡住的阻塞**（均记在 [设计](设计.md) 3.1），**现已解除**：

- **G14（内核侧）**：内核 crate 未开放模块可见性。已由内核侧在 `CopperCore/src-tauri/src/lib.rs` 开放 `pub mod registry / pub mod services / pub mod error / pub mod state` 解决。
- **G15（环境侧）**：内核依赖链需要 OpenSSL。Linux 类环境可用系统包管理器安装；本机 Windows 用 `CopperCore/.cargo/env-check.ps1` 预置 `OPENSSL_DIR`，构建前 dot-source 该脚本即可。

## 七、打包与发布

```
npm run build:frontend
npm run build:backend
npm run package -- --platform windows-x86_64 --backend target/release/copper_module_demo.dll
```

> G14（内核未开放 `pub mod`）与 G15（缺 OpenSSL 设备环境）两处此前阻塞后端构建的障碍已解除，`--backend target/release/copper_module_demo.dll` 的产物可正常生成本地文件。

### 脚本参数

`scripts/package-module.mjs` 支持以下参数：

| 参数 | 必填 | 默认值 | 说明 |
|---|---|---|---|
| `--platform <平台>` | 是 | 无 | 取值须属于 `platforms` 权威枚举，且必须已在 `module.json.platforms` 中声明 |
| `--backend <路径>` | 是 | 无 | 后端产物路径。期望文件名可由 `module.json.backend.artifact_glob` 推导 |
| `--frontend <目录>` | 否 | `module.json.frontend.dist` | **显式覆盖前端产物目录**。与 `--backend` 同为**可测性入口**，不改变默认链路，**不改变发布包结构契约** |
| `--out <目录>` | 否 | `dist-package` | 产物输出目录 |
| `--plan-only` | 否 | 否 | 只打印打包计划、不写出任何文件（CI 干跑） |

`--backend` 与 `--frontend` 的存在意义是**让打包逻辑可被测试**：测试用例可以自建临时夹具并指向它，而不必依赖仓库里已构建好的真实产物。默认路径始终取自 `module.json`，日常打包无需传这两个参数。

产物：

- `<id>-<version>-<platform>.cglm`（如 `copper-lamp.demo-tools-0.1.0-windows-x86_64.cglm`）
- 同名 `.sha256` 文件，内容为**单行小写十六进制 + 两空格 + 文件名**

`.cglm` 是 zip 容器，文件名承担类型标识作用。容器内部布局（冻结契约）：

```
module.json          清单（与仓库根同名文件一致）
manifest.sha256      包内逐文件校验清单
icon.svg             图标（从 assets/ 复制到包根）
backend/<产物>       后端产物
frontend/**          前端产物（register.js + assets）
LICENSE              许可文件（合规要求）
```

干跑（不产物，仅校验结构）：

```
npm run package -- --platform windows-x86_64 --backend <路径> --plan-only
```

**阶段一的分发形态**：内核当前只支持静态编译的内置模块，因此现在的产物用于**分发源码包 + 校验值**，供开发者自行编译，属于开发期分发，**不进入面向终端用户的一键安装链路**。包结构现在即按阶段二的最终形态定义，避免届时改契约。

tag 规范与 Release 检查见 [发布流程](发布流程.md)。

## 八、提审

链路：Release 正式发布 → `.github/workflows/module-submit.yml` 触发 → 校验 Release 资产齐全 → 生成 `cgl-libs` 条目 JSON → 向 `cgl-libs` 开 PR → 管理员审核合并后进入模块列表。

本地预览条目内容（不产生任何副作用）：

```
npm run submit
```

`npm run submit` 走 `--dry-run`，只打印将要写入 `cgl-libs` 的条目，不提交。

### 审核关注点

收录侧契约与红线见主仓库 `docs/cgl-libs.md`（审核红线 1.5、条目字段表 2.3.2、字段映射 2.3.6）。审核时重点检查三件事：

1. **包内容**是否与描述一致。
2. **权限声明**是否与代码行为一致——逐项核对 `permissions` 枚举，尤其是 `filesystem:game-dir` / `account:read` / `process:spawn`。
3. **作者身份**是否可追责（`author.url` 或 `author.email` 至少有一个，否则提审直接失败）。

### 被驳回的常见原因

| 原因 | 说明 |
|---|---|
| 权限与行为不一致 | 声明无 `network` 却发起出站请求；或声明了高危权限但 PR 中未说明理由 |
| `author` 无可追责联系方式 | `module.json.author.url` 与 `author.email` 皆缺 |
| `license` 与仓库 `LICENSE` 文件不一致 | 四处必须一致：`module.json.license`、仓库 `LICENSE`、README 声明、`cgl-libs` 条目 |
| `version` 与 tag 不符 | 三者必须严格一致：`module.json.version`、git tag（去 `v` 前缀）、`CHANGELOG.md` 版本段 |
| `platforms` 声明了但缺产物 | `platforms` 是承诺而非描述，缺产物即提审失败 |
| 未登记第三方二进制 | 随包分发的任何二进制必须登记在 `THIRD_PARTY_NOTICES.md` |
| `i18n_namespace` 与既有条目冲突 | 命名空间在全仓库内必须唯一 |

**第三方投递当前关闭**：收录侧规定，在模块隔离能力落地前只接受 `author.verified: true` 的官方条目，第三方 PR 一律 `rejected`。当前已落地的是权限强制侧（沙箱），**尚未落地**的是受管控子进程托管与 IPC 传输。因此本模板的提审链路可以跑通并产出正确条目，但第三方模块的正式收录要等隔离能力就绪。

## 九、版本与 CHANGELOG

- 版本号规则：`x.x.x`，**第一位保持 0**，第二位是大版本（重要更新），第三位是小版本（修复 bug 或小改动）。
- **模块作者不得自行变更版本号**，须由维护者下达指令。
- 更新顺序：先改 `module.json.version` → 再更新 `CHANGELOG.md` → 再更新 `README.md` 中过时的现状描述。
- 维护者确认通过后再打 tag、提交。

`CHANGELOG.md` 采用 Keep a Changelog 风格：

- 顶部为 `## [Unreleased]`，其下按 `Added` / `Changed` / `Deprecated` / `Removed` / `Fixed` / `Security` 分组。
- 每个已发布版本一段：`## [0.1.0] - <日期>`，与 git tag、`module.json.version` 三者严格一致（CI 校验 tag 与 manifest）。
- 版本段必须写清「相对上一版本的可见变化」，禁止只写「修复若干问题」。
- 重大变更需标注迁移说明：数据库迁移、权限新增、`api_version` 提升、`launcher.min` 提高。
- 破坏性变更在该版本段顶部显式标注 `BREAKING`。

完整流程见 [发布流程](发布流程.md)。
