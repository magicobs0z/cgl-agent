# 开发指南

本文是从零到提审的完整流程。硬契约细节（ABI、清单、能力、事件/意图/存储、权限）见 [模块契约](模块契约.md)；模块自身需求与架构见 [设计](设计.md)；版本、tag、Release 与提审链路见 [发布流程](发布流程.md)。

> 与旧版最大的不同：附加模块后端**不再与内核同进程、不再链接内核 crate**。它是一个独立 `cdylib`，由内核的 helper 子进程加载，只能通过版本化插件 ABI + 能力 RPC 与宿主交互。不要再去找 `KernelContext`、`migrate_scope`、`kernel.events()` 这类接口——它们只属于内置模块。
>
> **本模块迁移状态**：前后端均已迁移到插件 ABI。后端 `src-tauri/` 为 cdylib 插件（`lib.rs` 五个回调 + `host.rs` 能力 RPC + `contract.rs`/`state.rs`/`error.rs`，已删除 `module.rs` / `manifest.rs`），`cargo test` 35 项通过；前端已镜像 CopperModles 的适配（拆 `{ok,data}` 信封、概述字段 `noteCount`），`npm test` 17 项与 `vue-tsc` + vite 构建通过。**开始开发前的待办**：模块 id/命名空间仍是模板的 `copper-lamp.demo-tools` / `demo-tools`，与模板模块同 id，装进同一 `modules_dir` 会被重名拒绝——正式开发前需先确定自己的 id（见 [模块契约](模块契约.md) 第十四节）。

## 一、环境准备

| 组件 | 版本要求 | 说明 |
|---|---|---|
| Node.js | 24 | 与主仓库 `CopperCore/.github/workflows/` 的 CI 一致 |
| Rust | stable | 编译 `cdylib` 插件 |
| 平台 | Windows | 当前 `module.json.platforms` 只声明 `windows-x86_64` |

本仓库沿用 `CopperCore/` 的既有构建方式（`frontend/` 放 Vue 包、`src-tauri/` 放 Rust 插件 crate），便于在两个仓库之间迁移认知。

先确认工具链可用：

```
node --version
cargo --version
```

> 迁移完成后，后端唯一的内核侧依赖是 `copper-module-abi`（纯 Rust，不含 Tauri / 数据库 / OpenSSL），届时后端构建**不再需要 OpenSSL 环境**。当前（未迁移）仍依赖 `copper-core`，若构建报链接期缺 OpenSSL，可用 `CopperCore/.cargo/env-check.ps1` 预置 `OPENSSL_DIR`。

```
git clone <本仓库地址>
cd cgl-agent
npm install
npm run dev
```

`npm run dev` 启动 Vite 开发服务器（`vite --config vite.config.ts`，端口 1520，`strictPort`），宿主页为 `frontend/index.html`（`frontend/src/dev-preview.ts` 提供最小 Vue 宿主），用于独立预览模块页面。

## 三、改哪几个文件

迁移后，改这几组文件就能完成一次完整的模块开发。

| 文件 | 作用 | 改动时机 |
|---|---|---|
| `module.json` | 模块清单（唯一数据源）：id、i18n_namespace、版本、平台、权限、事件与意图声明、入口 | 每次身份、权限、事件/意图或元信息变化 |
| `src-tauri/src/lib.rs` | 插件入口：`init` / `start` / `invoke` / `stop` / `destroy` 与三条路由（event / intent / 命令） | 改生命周期或路由时 |
| `src-tauri/src/commands.rs` | 前端命令：解析 + 分发 + 响应信封 | 需要新的前后端通路时 |
| `src-tauri/src/contract.rs` | 对外契约常量（id、namespace、事件、意图），与清单逐项对照 | 改事件/意图声明时 |
| `frontend/src/register.ts` | 前端注册入口：`registerModule({ id, nav, routes })` | 改导航、路由、图标时 |
| `frontend/src/locales/*.json` | 语言包（扁平键，`zh-CN` 与 `en-US` 键集必须一致） | 任何时候新增文案 |

配套文件（按需改）：

| 文件 | 作用 |
|---|---|
| `src-tauri/src/host.rs` | 宿主能力客户端：`call_capability` + 输出缓冲扩容重试 |
| `src-tauri/src/service.rs` | 业务逻辑，与命令层解耦，便于单测 |
| `src-tauri/src/storage.rs` | 持久化：经 `storage.get/set/remove/list` 能力读写模块私有命名空间 |
| `src-tauri/src/state.rs` | 插件实例状态（宿主句柄、活动缓冲、运行标志） |
| `src-tauri/src/intents.rs` | 意图处理（`intent.<名>`）与发起（`intent.request`） |
| `src-tauri/src/error.rs` | 模块错误类型与响应信封映射 |
| `src-tauri/build.rs` | 构建期把 `module.json` 校验并注入编译期摘要 |
| `frontend/src/api.ts` | 模块命令类型化封装 + 信封拆解（禁止裸调 `invoke`） |
| `frontend/src/events.ts` | 模块订阅的内核事件类型化封装（注意 `.` → `-`） |
| `frontend/src/ModulePage.vue` 等页面 | 列表页与详情页 |
| `frontend/src/styles/module.css` | 模块私有样式，只消费 `var(--copper-*)` |

**命名纪律**：文件名写该文件的作用，不体现执行顺序。不要出现 `step1_init.rs`、`01_build.yml` 这类命名。

## 四、契约速查

完整版见 [模块契约](模块契约.md)。以下是日常最常用的部分。

### 后端：插件导出与生命周期

```rust
// 五个回调，统一用宏导出（不要手工拼函数表）
copper_module_abi::copper_module_plugin! {
    id = "copper-lamp.demo-tools",
    init = init,
    start = start,
    invoke = invoke,
    stop = stop,
    destroy = destroy,
}

// init：校验宿主 API → 读 config → 产出实例状态
unsafe extern "C" fn init(host: *const HostApi, config: AbiBytes, state_out: *mut *mut c_void) -> i32;
// start / stop：无参生命周期钩子
unsafe extern "C" fn start(state: *mut c_void) -> i32;
unsafe extern "C" fn stop(state: *mut c_void) -> i32;
// invoke：唯一调用入口，靠保留前缀区分事件 / 意图 / 命令
unsafe extern "C" fn invoke(state: *mut c_void, operation: AbiBytes, input: AbiBytes, output: *mut AbiBuffer) -> i32;
unsafe extern "C" fn destroy(state: *mut c_void);
```

### 后端：`invoke` 的三条路由

```rust
// event.<事件名>：宿主推送，返回值被忽略
if let Some(event) = operation.strip_prefix("event.") { /* 处理事件 */ }
// intent.<意图名>：宿主转发，返回值即意图响应（不套命令信封）
if let Some(intent) = operation.strip_prefix("intent.") { /* 处理意图 */ }
// 其它：前端命令，建议返回 `{ok,data}` / `{ok,error}` 信封
```

### 后端：输出缓冲协议

```rust
// 容量不足时必须写回所需长度再返回 BUFFER_TOO_SMALL，宿主据此扩容重试
fn write_output(output: &mut AbiBuffer, bytes: &[u8]) -> i32 {
    let required = bytes.len() as u64;
    if output.ptr.is_null() || output.capacity < required {
        output.len = required;                       // 关键：告诉宿主需要多大
        return ABI_STATUS_BUFFER_TOO_SMALL;
    }
    unsafe { std::ptr::copy_nonoverlapping(bytes.as_ptr(), output.ptr, bytes.len()); }
    output.len = required;
    ABI_STATUS_OK
}
```

### 后端：宿主能力（经 `HostClient::call`）

```rust
// 读 / 写模块私有存储（命名空间由会话身份决定）
host.call("storage.get",  &json!({ "key": "note.1" }))?;
host.call("storage.set",  &json!({ "key": "note.1", "value": { "title": "hi" } }))?;
host.call("storage.list", &json!({ "prefix": "note." }))?;
host.call("storage.remove", &json!({ "key": "note.1" }))?;

// 发布事件（需清单 events.publish 上界 + events 权限）
host.call("events.publish", &json!({ "name": "demo-tools.activity", "payload": {...} }))?;

// 发起意图（需 permissions 含 intents:request）
host.call("intent.request", &json!({ "intent": "expose.version", "payload": {} }))?;

// 自省
host.call("module.info", &json!({}))?;
```

### 前端：注册与命令

```ts
// 注册（每个模块恰好一次；重复 id 抛错）
registerModule({
  id: "copper-lamp.demo-tools",
  nav: { id: "copper-lamp.demo-tools", path: "/demo-tools",
         titleKey: "module.demo-tools.navTitle", icon: Puzzle },
  routes: [{ path: "/demo-tools", name: "demo-tools",
             component: () => import("./ModulePage.vue"),
             meta: { titleKey: "module.demo-tools.title" } }],
});
```

```ts
// 命令调用：附加模块经宿主桥，命令名与后端一致；失败装进信封由 callModule 拆解
const overview = await callModule<DemoOverview>("demo_tools_overview");
```

```ts
// 事件订阅（后端 `download.status` → 前端 `download-status`）
const un = await listen("download-status", (e) => { /* ... */ });
```

### 前端约定速查

| 项 | 要求 |
|---|---|
| 主题令牌 | 只用 `var(--copper-*)`（颜色 / 圆角 / 间距 / 尺寸 / 动效），禁止颜色字面量 |
| 图标 | 只用 `@lucide/vue` 图标组件，禁止 emoji |
| 通信 | 禁止裸调 `invoke`；附加模块经宿主桥 / 模块 `api.ts` 封装 |
| 事件 | 订阅内核事件时注意事件名中的 `.` 已转为 `-` |
| i18n | 文案零硬编码，全部走 `module.<i18n_namespace>.*` 键（**不是** `module.<id>.*`） |
| 语言包 | **扁平键**，命名空间**单段**，`zh-CN` 与 `en-US` 键集完全一致（CI 校验） |
| 性能 | 长列表虚拟滚动；流式/进度类事件节流，避免高频重渲染 |
| 页面级操作按钮 | 经 `#copper-titlebar-actions` Teleport 锚点注入标题栏 |

## 五、四个联动范例

### 范例一：订阅内核事件 `download.status`

场景：模块要在下载完成时做一次本地记录更新。

1. 清单声明订阅上界：

```json
"events": { "subscribe": ["download.status"], "publish": ["demo-tools.activity"] }
```

2. 插件在 `invoke` 的 `event.` 分支处理（宿主只在你声明的范围内推送）：

```rust
if let Some(event) = operation.strip_prefix("event.") {
    if event == "download.status" {
        // payload 为 DownloadTaskView 序列化结果（snake_case）
        let task_id = args.get("id").and_then(Value::as_u64);
        match args.get("status").and_then(Value::as_str) {
            Some("done") => { /* 更新本地记录 */ }
            Some("failed") | Some("cancelled") => { /* 落失败态 */ }
            _ => {}
        }
    }
}
```

要点：

1. **附加模块不补发历史事件**（内核用 `subscribe_from_now` 订阅）。需要初始快照就在 `start` 时主动查询，不要依赖事件补发。
2. **推送是异步的、有界的**：队列满（256）会丢弃并计数。插件处理过慢时会丢事件，重活应尽快返回。
3. **不要依赖"事件恰好一次"**：处理逻辑尽量幂等。
4. `events.subscribe` 为空 = 什么都不收；`events` 非空会在装载时自动获得沙箱 `Events` 能力。

同一个事件在前端的事件名是 `download-status`（`.` → `-`）。模板 `frontend/src/events.ts` 的 `onKernelDownloadStatus` 即此封装的现成实现。

### 范例二：发布模块自有事件

场景：模块状态变化时通知前端刷新。

1. 清单声明发布上界（**发布侧不允许裸 `*`**）：

```json
"events": { "publish": ["demo-tools.activity"] }
```

2. 经能力发布（两道闸：沙箱 `events` 权限 + 清单上界）：

```rust
host.call("events.publish", &json!({
    "name": "demo-tools.activity",
    "payload": { "kind": "module.start", "message": "...", "at": "..." }
}))?;
```

3. 前端监听 `demo-tools-activity`。

要点：

1. 发布失败**不应**把一次成功的数据操作改成失败：记录日志即可。
2. 事件名不在 `events.publish` 内会返回 `event_not_declared`。

### 范例三：发起意图 `expose.version`

场景：模块要拿到当前游戏版本清单，但版本扫描属于开始页模块的职责。模块之间不互相依赖，所以走意图。

1. 清单声明 `permissions: ["intents:request"]`（**只发起，不声明**该意图）。
2. 经能力发起：

```rust
let out = host.call("intent.request", &json!({ "intent": "expose.version", "payload": {} }))?;
// 返回 { "result": [ { "name": ..., "game_version": ..., "type": ..., "registered": ... } ] }
```

要点：

1. `expose.version` 由内置 `home` 模块声明，**不要**把内核已有意图写进自己的 `intents`（重复声明会让本模块装载失败并影响其它模块）。
2. 无处理器或超时返回 `intent_unavailable`，应作为可降级的能力缺失处理；权限拒绝等返回 `intent_failed`，不应被当作"稍后重试即可"。
3. 声明自己的意图处理器时，意图名要带模块域前缀，避免撞名。

### 范例四：持久化一条记录（模块私有存储）

```rust
// 自增 id 用 KV 存下一个值；列表用前缀查询后在模块侧排序
let next = host.call("storage.get", &json!({ "key": "meta.next-id" }))?;
host.call("storage.set", &json!({ "key": "note.1", "value": { ... } }))?;
let keys = host.call("storage.list", &json!({ "prefix": "note." }))?;
```

要点：

1. 模块**拿不到内核数据库**，也不再写迁移；持久化只有 KV 原语。
2. 命名空间由会话身份决定，模块无法访问别人的数据。
3. 单模块命名空间上限 4 MiB，单键上限 256 字节；超限返回 `storage_quota_exceeded`。
4. 过滤、排序、分页在**模块侧**完成。

## 六、调试

### 同步进启动器模块目录

```
npm run import:dev
npm run import:dev:watch
```

`scripts/import-dev-module.mjs` 的行为：解析 `module.json` → 构建前端与后端 → 目标目录 `<modules_dir>/<id>/` → 原子替换 `backend/` 与 `frontend/` → 写 `dev.json` → 打印「请在启动器设置 → 模块 中启用并重启加载」。

目录约定（内核已存在 `Paths::modules_dir()`，Windows 下为 `%APPDATA%\copper-lamp\copper-golem\modules`）：

```
<modules_dir>/
└─ copper-lamp.demo-tools/
   ├─ module.json      清单
   ├─ backend/         后端 cdylib 产物（helper 用 libloading 加载）
   ├─ frontend/        前端产物（register.js + assets）
   └─ dev.json         开发模式标记（仅本地调试，不入发布包）
```

**前置条件**：内核需要能定位 helper 可执行文件 `copper-module-helper`（与主程序同目录，或主程序目录的上一级）。开发/测试场景可用环境变量 `COPPER_MODULE_HELPER` 显式指定路径；找不到 helper 时模块会以装载失败告终，不会静默降级。

### 日志

内核日志由 `tauri-plugin-log` 统一写出，日志目录为 `Paths::logs_dir()`。插件自身的诊断写到子进程 **stderr**，内核会在装载/调用失败时把 stderr 尾部附进错误信息（`helper_backend.rs::wrap_with_stderr`），因此优先看内核日志里的错误文本。

### 常见「没反应」排查表

| 症状 | 最可能的原因 | 核对方法 |
|---|---|---|
| 模块没被扫描到 | 目录名不是合法两段式 id | 目录名必须等于 `module.json.id` |
| 状态 `failed` | `init`/`start` 返回 `Err`、清单校验不过、找不到 helper | 看内核日志与 `modules_list` 暴露的错误文本；用 `COPPER_MODULE_HELPER` 指定 helper |
| 插件「能被扫描但不被加载」 | 手工拼函数表导致 `struct_size` / `abi_version` / `module_id` 漂移 | 用导出宏；`init` 中调用 `host.validate()` |
| 左导航没有入口 | 前端入口未在磁盘 / 模块未启用 / 入口脚本未调用宿主桥 | 核对 `modules_frontends` 返回值；入口脚本经 `window.__COPPER_HOST__.registerModule` 登记 |
| 点进去空白 | `nav.path` 与 `routes[].path` 不一致 | 两者逐字相同 |
| 文案显示键名 | 语言包未注册，或键前缀用了完整 `id` | 键前缀必须是 `module.<i18n_namespace>.*` |
| 部分文案回退英文或键名 | `zh-CN` / `en-US` 键集不一致 | `npm run schema:check` |
| 命令失败看不到原因 | 插件只回状态码，前端没拆信封 | 插件把失败装进 `{ok:false, error}`；前端封装拆信封 |
| 事件收不到 | 事件名不在 `events.subscribe` 内 / 未获 `Events` 权限 / 模块未 `start` | 核对清单模式与沙箱授权 |
| 事件洪峰丢事件 | 队列容量 256 | 观察 `AddonEventBridge::dropped()`；插件处理过慢会出现 |
| 发布事件报 `event_not_declared` | 事件名不在 `events.publish` 内 | 补清单，或用自证域前缀 `<域>.*` |
| 意图报 `intent_unavailable` | 无模块声明该意图 / 转发超时 | 确认目标模块已 `start`；据此降级 |
| 意图报 `intent_failed` | 权限拒绝 / 目标未运行 | 修权限或目标状态，不是重试问题 |
| 存储报 `storage_quota_exceeded` | 单模块超过 4 MiB | 模块侧控制数据量 |
| 存储报 `storage_corrupt` | `storage.json` 损坏 | 内核刻意报错而不静默重置 |
| `error[E0603]: module ... is private` | 误去依赖内核 crate | 插件只依赖 `copper-module-abi` |

## 七、打包与发布

```
npm run build:frontend
npm run build:backend
npm run package -- --platform windows-x86_64 --backend target/release/copper_module_demo.dll
```

### 脚本参数

`scripts/package-module.mjs` 支持以下参数：

| 参数 | 必填 | 默认值 | 说明 |
|---|---|---|---|
| `--platform <平台>` | 是 | 无 | 取值须属于 `platforms` 权威枚举，且必须已在 `module.json.platforms` 中声明 |
| `--backend <路径>` | 是 | 无 | 后端产物路径。期望文件名可由 `module.json.backend.artifact_glob` 推导 |
| `--frontend <目录>` | 否 | `module.json.frontend.dist` | 显式覆盖前端产物目录。与 `--backend` 同为**可测性入口**，不改变默认链路与包结构契约 |
| `--out <目录>` | 否 | `dist-package` | 产物输出目录 |
| `--plan-only` | 否 | 否 | 只打印打包计划、不写出任何文件（CI 干跑） |

产物：

- `<id>-<version>-<platform>.cglm`（如 `copper-lamp.demo-tools-0.1.0-windows-x86_64.cglm`）
- 同名 `.sha256` 文件，内容为**单行小写十六进制 + 两空格 + 文件名**

`.cglm` 是 zip 容器，文件名承担类型标识作用。容器内部布局（冻结契约）：

```
module.json          清单（与仓库根同名文件一致）
manifest.sha256      包内逐文件校验清单
icon.svg             图标（从 assets/ 复制到包根）
backend/<产物>       后端 cdylib
```

## 八、提审

链路：Release 正式发布 → `.github/workflows/module-submit.yml` 触发 → 校验 Release 资产齐全 → 生成 `cgl-libs` 条目 JSON → 向 `cgl-libs` 开 PR → 管理员审核合并后进入模块列表。

本地预览条目内容（不产生任何副作用）：

```
npm run submit
```

### 审核关注点

收录侧契约与红线见主仓库 `docs/cgl-libs.md`（审核红线 1.5、条目字段表 2.3.2、字段映射 2.3.6）。审核时重点检查三件事：

1. **包内容**是否与描述一致。
2. **权限声明**是否与代码行为一致——逐项核对 `permissions`，以及 `events` / `intents` 声明的上界是否与实际使用相符。
3. **作者身份**是否可追责（`author.url` 或 `author.email` 至少有一个，否则提审直接失败）。

### 被驳回的常见原因

| 原因 | 说明 |
|---|---|
| 权限与行为不一致 | 声明无 `network` 却发起出站请求；或声明了高危权限但 PR 中未说明理由 |
| 事件/意图声明超出实际使用 | `events.publish` 声明了过宽的域前缀；声明了不处理的意图 |
| `author` 无可追责联系方式 | `module.json.author.url` 与 `author.email` 皆缺 |
| `license` 与仓库 `LICENSE` 文件不一致 | 四处必须一致：`module.json.license`、仓库 `LICENSE`、README 声明、`cgl-libs` 条目 |
| `version` 与 tag 不符 | 三者必须严格一致：`module.json.version`、git tag（去 `v` 前缀）、`CHANGELOG.md` 版本段 |
| `platforms` 声明了但缺产物 | `platforms` 是承诺而非描述，缺产物即提审失败 |
| 未登记第三方二进制 | 随包分发的任何二进制必须登记在 `THIRD_PARTY_NOTICES.md` |
| `i18n_namespace` 与既有条目冲突 | 命名空间在全仓库内必须唯一 |

**第三方投递当前关闭**：收录侧规定，在模块隔离能力落地前只接受 `author.verified: true` 的官方条目，第三方 PR 一律 `rejected`。当前已落地的隔离是「受管控子进程 + 版本化 IPC/ABI」；尚未闭合的是插件无法注册 i18n 语言包、能力错误不可细分等缺口（见 [模块契约](模块契约.md) 第十四节）。

## 九、版本与 CHANGELOG

- 版本号规则：`x.x.x`，**第一位保持 0**，第二位是大版本（重要更新），第三位是小版本（修复 bug 或小改动）。
- **模块作者不得自行变更版本号**，须由维护者下达指令。
- 更新顺序：先改 `module.json.version` → 再更新 `CHANGELOG.md` → 再更新 `README.md` 中过时的现状描述。
- 维护者确认通过后再打 tag、提交。

`CHANGELOG.md` 采用 Keep a Changelog 风格：

- 顶部为 `## [Unreleased]`，其下按 `Added` / `Changed` / `Deprecated` / `Removed` / `Fixed` / `Security` 分组。
- 每个已发布版本一段：`## [0.1.0] - <日期>`，与 git tag、`module.json.version` 三者严格一致（CI 校验 tag 与 manifest）。
- 版本段必须写清「相对上一版本的可见变化」，禁止只写「修复若干问题」。
- 重大变更需标注迁移说明：权限新增、`api_version` 提升、`launcher.min` 提高。
- 破坏性变更在该版本段顶部显式标注 `BREAKING`。

完整流程见 [发布流程](发布流程.md)。
