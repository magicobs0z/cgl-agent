# 模块契约

本文摘录铜内核（`CopperCore`）对**附加模块**的硬契约。所有条目均以 `CopperCore` 真实源码为准，逐条标注出处文件路径，不包含推测内容。

> 权威设计文档：`D:\CopperGolem\docs\cgl-models.md`（主仓库）。
> 收录侧契约：`D:\CopperGolem\docs\cgl-libs.md`。
> 读法：本文写的「当前」「尚未实现」均指 `CopperCore` 源码的现状，不是本模块的取舍。

**阅读前必须知道的一件事**：附加模块后端**不再与内核同进程**。它是被内核的受监管子进程（helper）用 `libloading` 加载的独立 cdylib，只能通过版本化的插件 ABI 与 IPC 协议与内核对话。理解偏差的典型表现是「代码编译通过、运行起来没反应」或「调用报错但看不到原因」（见文末排查表）。

## 一、三层契约与版本边界

出处：`CopperCore/copper-module-abi/src/{ipc.rs,plugin_abi.rs}`、`registry/manifest.rs`

三个版本号**彼此独立**，禁止合并成一个：

| 边界 | 常量 | 当前值 | 出处 |
|---|---|---|---|
| 内核 ↔ helper（IPC 协议） | `ipc::PROTOCOL_VERSION` | `1` | `copper-module-abi/src/ipc.rs` |
| helper ↔ 插件（插件 ABI） | `plugin_abi::ABI_VERSION` | `1` | `copper-module-abi/src/plugin_abi.rs` |
| 模块清单 schema | `manifest::SUPPORTED_SCHEMA_VERSION` | `"1"` | `registry/manifest.rs` |
| 模块 API 版本 | `manifest::SUPPORTED_API_VERSION` | `1` | `registry/manifest.rs` |

协商规则：helper 在收到任何方法前必须先完成 `module.handshake`，双方各自拒绝不支持的版本；插件侧由 `HostApi::validate()` 与 `PluginFunctionTable::validate()` 在初始化时校验 `struct_size` 与 `abi_version`，任一不符即拒绝装载。

`copper-module-abi` 是内核与附加模块之间**唯一的共享边界**，被三方复用：铜内核（宿主）、`copper-module-helper`（子进程）、附加模块。附加模块只依赖本 crate 即可实现 ABI，**不链接内核**（更不涉及 Tauri）。

## 二、运行形态：受监管子进程

出处：`registry/helper_backend.rs`、`copper-module-abi/src/{helper_runtime.rs,helper_client.rs}`

```
内核进程                                  helper 子进程（copper-module-helper）
AddonProxyModule ──stdin/stdout(帧)──▶  HelperRuntime ──libloading──▶ 插件 cdylib
```

- **插件不自行声明身份**：模块 id 由宿主在派生 helper 时经 `--module-id` 下发，helper 只把它交给插件上下文。插件函数表里声明的 `module_id` 必须与宿主下发的**逐字一致**，否则 `PluginInstance::instantiate` 以 `ModuleIdMismatch` 拒绝（`plugin_abi.rs::validate`）。
- **插件不链接内核**：拿不到 `KernelContext`、数据库连接、事件总线对象。一切宿主能力经能力 RPC（见第五节）。
- **回调串行**：helper 主循环一次只处理一帧消息，插件的 `invoke` 回调发生在同一线程，实例状态用 `&mut` 独占即可，不需要 `Arc<Mutex<...>>`。
- **插件崩溃不带走启动器**：helper 进程隔离；内核按超时与进程退出如实报错（`helper_client.rs`）。

### 生命周期与会话时序

出处：`helper_backend.rs::AddonSession`、`helper_client.rs::HelperProcess`

```
spawn(helper, --module-id, --plugin)
  → handshake（协商 PROTOCOL_VERSION）
  → module.initialize(config)   # helper 加载 cdylib 并调用插件 init
  → module.start                # 起插件 + 登记事件订阅 / 意图处理器
  → module.invoke / intent.handle（任意次）
  → module.stop                 # 撤登记 + 插件 stop
  → 关闭 stdin → 等待退出（超时强杀）
```

| 阶段 | 超时 | 出处 |
|---|---|---|
| handshake | 10s | `helper_backend.rs` |
| initialize | 20s | 同上 |
| start / stop | 10s | 同上 |
| invoke | 60s | 同上 |
| intent 转发 | 10s | 同上（`INTENT_FORWARD_TIMEOUT`） |
| shutdown | 10s | 同上 |

`init` 时宿主下发配置（`AddonProxyModule::init_module`）：

```json
{ "module_dir": "<模块安装目录>", "module_version": "<清单版本>" }
```

插件**无法自行声明身份或扩大输入范围**，配置内容由宿主组装。

## 三、`module.json` 清单

出处：`registry/manifest.rs`（内核侧唯一表达，字段名 snake_case，与 `module.schema.json` 逐字对齐）

| 字段 | 类型 | 说明 |
|---|---|---|
| `schema_version` | string | 必须为 `"1"`，高于此值拒绝，不做尽力解析 |
| `id` | string | 全局唯一，两段式 `author.module`（见下） |
| `i18n_namespace` | string | 单段命名空间；**必须等于 `id` 的最后一段** |
| `display_name` / `description` | string | 非空 |
| `i18n` | object | locale → `{display_name, description}` 本地化覆盖，可选 |
| `author` | object | `{name, email?, url?}` |
| `license` | string | SPDX 标识 |
| `version` | string | 可解析 semver（`MAJOR.MINOR.PATCH`） |
| `platforms` | string[] | 非空，取值见下 |
| `launcher` | object | `{min, max?}` 内核兼容区间（semver） |
| `api_version` | number | 必须为 `1` |
| `backend` | object | `{crate, entry, artifact_glob}`，非空 |
| `frontend` | object | `{dist, register}` |
| `permissions` | string[] | 权限声明（授权上界），可为空 |
| `events` | object | `{subscribe: [...], publish: [...]}`，可为空 |
| `intents` | string[] | 声明的意图处理器上界，可为空 |
| `icon` / `category` / `keywords` / `homepage` / `donation` / `changelog` | — | 可选元信息 |

### id 形态

出处：`registry/modules.rs::is_valid_module_id`

`^[a-z0-9]+(-[a-z0-9]+)*(\.[a-z0-9]+(-[a-z0-9]+)*)+$`，段数 ≥ 2，总长 ≤ 128。

校验是安全边界的第一道闸：id 会被直接当作**目录名**使用，放行 `..`、`/`、`\`、盘符或 Windows 保留名会让扫描与卸载越过 `modules_dir`。

### i18n 命名空间规则

出处：`registry/manifest.rs::is_i18n_namespace`

单段、以字母开头、仅含小写字母/数字/连字符、长度 3~32、**不含点号**，且等于 `id` 的第二段。二者漂移会让前端拼键与后端注册指向两个命名空间，表现为文案整体回退键名（历史同类 bug 的高发点）。

### platforms 权威枚举

`windows-x86_64` / `windows-aarch64` / `android-arm64` / `linux-x86_64`。

装载时三重门禁（`loader.rs::load_one_inner`）：平台命中当前目标、`launcher` 区间覆盖当前内核版本（比对 `CARGO_PKG_VERSION`）、`api_version` 匹配。

### events 声明

出处：`manifest.rs::validate`

`subscribe` 与 `publish` **分开声明**：能**收**某事件不代表能**发**它，合成一个列表等于允许模块冒充内核事件源（内核事件会被桥接到前端监听器）。

事件模式只允许三种形态：

- `*`（**仅订阅侧**允许）；
- `<点分段名>.*`（自证域前缀）；
- `<点分段名>`（精确名）。

每段只含小写字母/数字/连字符，总长 ≤ 128；同侧不允许重复。**发布侧禁裸 `*`**，否则模块可以任意名字发布，包括冒充内核事件名。

两个列表都为空表示既不收也不发（空 = 不许，与 `permissions` 同一口径）。

### intents 声明

点分隔的小写字母/数字/连字符分段名，**不允许通配**，总长 ≤ 128，不允许重复。声明的是「本模块**处理**哪些意图」；插件**发起**意图请求是另一个方向，需要 `permissions` 含 `intents:request`。

## 四、后端插件 ABI

出处：`copper-module-abi/src/plugin_abi.rs`、`plugin_export.rs`

### 依赖与产物

```toml
[lib]
name = "copper_module_demo"
crate-type = ["cdylib", "rlib"]   # cdylib 交付；rlib 供自身单测链接

[dependencies]
copper-module-abi = { path = "../../CopperCore/copper-module-abi" }
serde = { version = "1", features = ["derive"] }
serde_json = "1"
thiserror = "2"
log = "0.4"
```

产物文件名由清单 `backend.artifact_glob` 的主干跨平台匹配（`BackendSpec::artifact_stem`）：同一份源码在 Windows/Linux/macOS 上产出 `.dll`/`.so`/`.dylib` 都能命中。

### 导出宏

插件作者**不应手工拼 `PluginFunctionTable`**（结构布局、版本号、模块 id 编码任一写错都会导致「能被扫描但不被加载」的隐蔽故障）。用宏只暴露五个回调：

```rust
copper_module_abi::copper_module_plugin! {
    id = "copper-lamp.demo-tools",
    init = init,
    start = start,
    invoke = invoke,
    stop = stop,
    destroy = destroy,
}
```

宏生成 `#[no_mangle] copper_module_plugin_entry`，回填 `struct_size` / `abi_version` / `module_id` / 五个回调指针。

### 回调签名与语义

```rust
// init：校验宿主 API → 读 config → 产出实例状态
unsafe extern "C" fn init(host: *const HostApi, config: AbiBytes, state_out: *mut *mut c_void) -> i32;

// start / stop：无参生命周期钩子，串行调用
unsafe extern "C" fn start(state: *mut c_void) -> i32;
unsafe extern "C" fn stop(state: *mut c_void) -> i32;

// invoke：所有「调用」的唯一入口，靠保留前缀区分来源
unsafe extern "C" fn invoke(state: *mut c_void, operation: AbiBytes, input: AbiBytes, output: *mut AbiBuffer) -> i32;

// destroy：归还实例状态（可重复调用；宿主 drop 时也会补一次）
unsafe extern "C" fn destroy(state: *mut c_void);
```

### `invoke` 的三条路由

`event.` 与 `intent.` 是**宿主保留前缀**，模块不得注册同名命令（`ipc.rs::PLUGIN_COMMAND_EVENT_PREFIX` / `PLUGIN_COMMAND_INTENT_PREFIX`）。

| 前缀 | 来源 | 返回值语义 |
|---|---|---|
| `event.<事件名>` | 宿主推送的内核事件 | 宿主**忽略**返回值 |
| `intent.<意图名>` | 宿主转发的他人意图请求 | 返回值即意图响应，回给请求方 |
| 其它（无前缀） | 前端经 `module_invoke` 调用的模块命令 | 返回值即命令结果（建议套信封，见第十节） |

### 状态码与输出缓冲协议

| 状态码 | 值 | 含义 |
|---|---|---|
| `ABI_STATUS_OK` | 0 | 成功 |
| `ABI_STATUS_ERROR` | 1 | 失败 |
| `ABI_STATUS_BUFFER_TOO_SMALL` | 2 | 输出缓冲不足 |
| `ABI_STATUS_NOT_SUPPORTED` | 3 | 宿主明确拒绝/未实现该能力，插件不得据此猜测成功 |

输出缓冲规则（`plugin_abi.rs::call_with_growing_buffer`）：

- 宿主首次给 `INITIAL_OUTPUT_CAPACITY = 512` 字节；不足时插件**必须**把所需长度写回 `output.len` 再返回 `BUFFER_TOO_SMALL`，宿主据此扩容重试（初始容量上限重试 8 次）。
- 单次缓冲上限 `MAX_ABI_BUFFER_BYTES = 8 MiB`；超过直接拒绝。
- 返回 `OK` 时 `output.len` 不得大于 `output.capacity`，否则判为契约违约（`ContractViolation`），宿主不会读取越界内容。

### 载荷编码

跨 ABI 的 `operation` / `input` / 输出统一为 **UTF-8 JSON**。`input` 为空字节数组时按 `Value::Null` 处理（`helper_runtime.rs`）。

## 五、宿主能力 RPC

出处：`registry/capability.rs`、`copper-module-abi/src/helper_client.rs::CapabilityDispatcher`

插件经 `HostApi::call_capability(user_data, capability, input, output)` 请求宿主能力。helper 只做搬运，**宿主是唯一能决定「是否授权」的一方**，未知能力默认拒绝。

### 能力表

| 能力 | 参数 | 返回 | 授权要求 |
|---|---|---|---|
| `module.info` | 无 | `{id, origin, running}` | 会话身份必须已注册 |
| `storage.get` | `{key}` | `{value}`（不存在为 `null`） | 会话身份命名空间 |
| `storage.set` | `{key, value}` | `{stored: true}` | 同上 |
| `storage.remove` | `{key}` | `{removed: bool}` | 同上 |
| `storage.list` | `{prefix?}` | `{keys: [...]}`（字典序） | 同上 |
| `intent.request` | `{intent, payload?}` | `{result}` | 需 `intents:request` 权限 |
| `events.publish` | `{name, payload?}` | `{published: true}` | 需 `events` 权限 + 清单 `events.publish` 上界 |

参数解析用 `deny_unknown_fields` + 严格类型：多余字段直接拒绝，避免「传错字段名却静默成功」。

### 身份只来自会话

能力参数**顶层**不得携带 `module_id`（`ipc.rs::deserialize_capability_params` 在协议层拒绝）。真正的防护是宿主始终使用**会话绑定**的模块身份，从不读取请求里的任何身份字段。嵌套的 `module_id` 是模块自己的数据，不构成身份伪造。

### 错误码

| 错误码 | 含义 |
|---|---|
| `capability_not_supported` | 本构建未实现该能力（默认拒绝） |
| `capability_denied` | 沙箱越权（用户收紧或未授权） |
| `invalid_capability_params` | 参数不合规 |
| `unknown_module` | 会话身份未注册（`module.info`） |
| `event_not_declared` | 事件名不在 `events.publish` 上界内 |
| `intent_unavailable` | 无模块声明该意图 / 转发超时（**插件可据此降级**） |
| `intent_failed` | 其余意图失败（含权限拒绝、目标未运行），**不该被当作稍后重试即可** |
| `storage_invalid_key` / `storage_quota_exceeded` / `storage_corrupt` / `storage_io_error` | 存储侧细分错误 |

**已知缺口（风险）**：插件 ABI 的 `call_capability` **只回状态码**，没有结构化错误通道。helper 只把 `capability_not_supported` 映射为 `ABI_STATUS_NOT_SUPPORTED`，其余一律 `ABI_STATUS_ERROR`。因此插件**无法区分**「权限拒绝」「参数错误」「意图无声明」等具体原因。若要给插件可诊断的错误，需要在内核/helper 侧输出错误 DTO 并扩展 ABI——当前未做。

## 六、事件

### 订阅（内核 → 插件）

出处：`registry/addon_events.rs`、`helper_backend.rs::register_events`

- **声明即上界**：只有命中清单 `events.subscribe` 模式的事件才会推送；空声明表示什么都不收。
- **登记时机**：模块 `start` 成功后 `AddonEventBridge::register`；`stop` 时 `unregister`（置停止位 → 清空待推送 → 唤醒 → join 推送线程 → 删条目）。顺序即正确性，反了会把事件送给正在退出的插件。
- **不补发历史**：用 `subscribe_from_now("*")` 订阅，附加模块**不补发**重放缓冲内的历史事件。子进程无从区分「刚发生」与「补发的旧事」，补发会让 `version.installed` 这类带副作用的处理被重复执行。
- **异步推送**：`EventBus::publish` 是同步分发，回调跑在发布方线程上，因此回调**只做过滤与非阻塞入队**，真正的写管道由每模块**一条专属推送线程**独占，避免「某模块卡顿」升级为「内核功能卡顿」。
- **有界队列**：`QUEUE_CAPACITY = 256`，满则丢弃并计数（`AddonEventBridge::dropped()`），不会把内核内存吃光。
- **命令映射**：helper 收到事件后转成一次插件调用 `event.<事件名>`；**这是单向通知，helper 不回帧**（回帧会打乱宿主的请求/响应配对）。
- **能力往返期间的延迟队列**：插件在一次能力调用未返回时，宿主同时推来的事件会进入有界延迟队列（容量 256），由主循环排空；不会就地重入插件。

授权判定：装载时 `events` 任一方向非空即授予沙箱 `Events`；`start` 前再 `enforce` 一次，使用户在设置页收紧权限真的生效。

### 发布（插件 → 内核）

出处：`registry/capability.rs::CAPABILITY_EVENTS_PUBLISH`

经 `events.publish` 能力发布，两道闸缺一不可：

1. 沙箱 `Permission::Events`（用户可收紧）；
2. 清单 `events.publish` 上界（发布侧禁裸 `*`）。

未声明的事件名返回 `event_not_declared`。发布成功后进入内核 `EventBus`，与其它事件一样桥接前端。

### 前端桥接：`.` → `-`

出处：`registry/events.rs`（`app.emit(&name.replace('.', "-"), &payload)`）

Tauri 事件名不允许 `.`，桥接前端时统一映射为连字符：

| 后端事件名 | 前端监听名 |
|---|---|
| `download.status` | `download-status` |
| `version.installed` | `version-installed` |
| `demo-tools.activity` | `demo-tools-activity` |

该转换**只对事件名生效**，模块 `id` 本身不进入事件名（`id` 含点号不影响此处）。

内核侧已发布事件（以源码为准，供命名避让）：`download.created` / `download.progress` / `download.status`、`settings.changed`、`account.changed` / `account.login.state`、`update.status`、`version.installed` / `version.removed`、`versions.changed`、`game.launched`、`content-download.location`、`game-download.enqueued` / `game-download.installed` / `game-download.failed` / `game-download.cancelled`。

模块自建事件建议用 `<模块域>.<动名词>`，避免与上表撞名。

## 七、意图

意图是**双向**语义，两个方向各有各的上界。

### 声明处理器（他人 → 本模块）

出处：`helper_backend.rs::register_intents`、`helper_runtime.rs::dispatch(IntentHandle)`

- 清单 `intents` 列出本模块处理的意图（空 = 不处理任何）。
- 模块 `start` 成功后按清单逐个 `declare_checked`（附加模块必须持 `intents` 权限）；`stop` 时 `withdraw` 注销全部。
- 转发路径：他人 `intents.request(intent, payload)` → 宿主 → helper `intent.handle` → 插件 `invoke("intent.<意图名>", payload)`。
- 插件返回值**即意图响应**，回给请求方，**不能套前端命令信封**。
- 转发带 10s 超时与「带超时地拿会话锁」：目标模块可能正持锁跑长命令，而它的插件此刻又在等宿主能力响应，无限等待就是闭环死锁。自调用必然命中这条路径，因此必须是「显式拒绝」而不是 hang 住。

### 发起请求（本模块 → 他人）

出处：`registry/capability.rs::CAPABILITY_INTENT_REQUEST`

- 需要 `permissions` 含 `intents:request`（映射到沙箱 `Permission::Intents`）。
- 经 `intent.request` 能力发起，复用既有能力通道，**不需要新增 IPC 方法与 ABI 字段**。
- 返回 `{result}`；`intent_unavailable` 表示没有处理器或超时，插件据此降级是合理的。

## 八、模块私有存储

出处：`registry/module_storage.rs`

模块**不能**直接用内核数据库（`DatabaseService` 暴露的 `with_conn(闭包)` 无法跨进程传递；直接开放 SQL 会绕过表结构与迁移约束，插件还能读别人的表）。改为**有界的具名键值操作**：

- 命名空间由**会话身份**决定，模块无法跨命名空间访问。
- 落点：`<data_dir>/module_data/<module_id>/storage.json`。
- 写入先落 `.tmp` 再原子 `rename`，中断不会留下半截 JSON。
- 文件损坏时**报错而不是静默重置**（`storage_corrupt`）。
- 容量：单模块 `MAX_NAMESPACE_BYTES = 4 MiB`；单键 `MAX_KEY_BYTES = 256`。
- 值形状为任意 JSON；列表按 key 字典序，支持前缀过滤。

过滤、排序、分页等查询语义需在**模块侧**完成（存储只提供键值原语）。

## 九、权限

出处：`registry/loader.rs::declared_permissions`、`registry/sandbox.rs`

清单 `permissions` 用**细粒度**枚举（权威定义见主仓库 `docs/cgl-libs.md` 2.3.6）；沙箱是**粗粒度**的 9 项执行侧枚举。装载时做**保守映射**：只有能无歧义对应的才授予，其余如实不授予并留 warning（宁少不多）。

| 清单权限 | 沙箱权限 |
|---|---|
| `filesystem:read` / `filesystem:write` / `filesystem:game-dir` | `FileSystem`（沙箱当前不区分读写与游戏目录） |
| `network` | `Network` |
| `process:spawn` | `SpawnProcess` |
| `settings:write` | `Settings` |
| `intents:request` | `Intents` |
| `account:read` / `download:enqueue` | **暂无对应能力，不授予**（留 warning） |
| （`events` 任一方向非空） | `Events`（由 `events` 声明派生，不在 `permissions` 里重复声明） |
| 未知取值 | 不授予（留 warning） |

沙箱语义（`sandbox.rs`）：`grant`（登记授权，含模块目录）、`knows`、`is_allowed`、`enforce`（越权留痕 + 超限强制停用）、`is_suspended`、`grants`、`revoke_permission` / `restore_permission`（**用户只能收紧不能提权**）。

**即便权限声明为空也必须登记沙箱**：`knows` 以「是否登记」区分附加模块与内置模块，未登记的模块会被当作内核内置而豁免校验。空权限登记才能让「声明为空 = 什么都不许」成立，而不是「声明为空 = 不受管」。

## 十、前端契约

### 运行期装配

出处：`registry/frontend.rs`、`commands/modules.rs::modules_frontends`、`frontend/src/modules/addonRuntime.ts`

附加模块前端在**运行期**才出现在磁盘上，无法被宿主编译期静态 `import`。装配流程：

1. 内核注册自定义协议 `cglmod`，把 `<modules_dir>/<id>/frontend/**` 暴露为 HTTP 资源（Windows/安卓形如 `http://cglmod.localhost/<id>/register.js`，其它平台形如 `cglmod://localhost/<id>/register.js`）。
2. 前端 Shell 启动后调用 `modules_frontends`，取回已启用、且磁盘上确有入口脚本的模块清单：`{id, namespace, entry_url, style_urls}`。
3. 逐个注入样式、安装宿主桥、动态 `import(entry_url)`。
4. 单个模块加载失败只记录并跳过，不阻断内置界面，也不影响其它模块。

### 宿主桥（`window.__COPPER_HOST__`）

```ts
interface CopperHostBridge {
  registerModule(registration: { nav: {path, titleKey, icon}, routes: RouteRecordRaw[] }): void;
  invoke(command: string, args?: unknown): Promise<unknown>;   // 只允许本模块自身命令
}
```

- 桥**一次只服务一个模块**，加载完即清空 `window.__COPPER_HOST__`，防止后加载脚本冒充前一模块身份。
- `registerModule` 里的 `id` 由**宿主绑定**，模块无权声明；`invoke` 固定带上宿主绑定的 `moduleId`。
- 这与内核 `registry.ts::registerModule`（内置模块用的静态注册表）是**同一个注册表**，只是附加模块经桥间接调用。

### 命令调用链路

```
前端 host.invoke(command, args)
  → 内核命令 module_invoke(moduleId, command, args)
  → ModuleRegistry::invoke → AddonProxyModule::invoke
  → helper module.invoke
  → 插件 invoke(state, "<command>", args, output)
```

`module_invoke` 是附加模块的**唯一后端能力通道**（内置模块命令在静态命令表中，不走此路径）。

### 命令响应信封（约定）

插件 ABI **没有结构化错误通道**（`invoke` 只回状态码），因此前端命令失败必须由模块自己装进 JSON 信封：

```json
{ "ok": true,  "data": { ... } }
{ "ok": false, "error": { "kind": "...", "message": "..." } }
```

前端封装负责拆信封：`ok:false` 时抛出携带模块错误分类与文案的异常，**不把 `ok:false` 当成功读**（否则页面显示空数据）。

### `registerModule` 前端注册契约

出处：`frontend/src/modules/registry.ts`

```ts
interface ModuleNavItem { id: string; path: string; titleKey: string; icon: Component }
interface ModuleFrontend { id: string; nav: ModuleNavItem; routes: RouteRecordRaw[] }
function registerModule(module: ModuleFrontend): void;
```

硬约定：

1. 每个模块**恰好调用一次**；重复 `id` 直接 `throw`，不静默覆盖。
2. 注册顺序即左导航顺序。
3. `nav.path` 必须与 `routes[].path` 逐字一致（不一致表现为「导航出现但点进去空白」）。
4. `routes[].meta.titleKey` 驱动标题栏标题。
5. 语言包与 `t()` 键一律用 `module.<i18n_namespace>.*`（**不是** `module.<id>.*`）。
6. 主题令牌只用 `var(--copper-*)`，图标只用 `@lucide/vue` 图标组件，禁止 emoji。

## 十一、两段式 id 与 i18n 命名空间解耦

出处：`services/i18n.rs::lookup`（`key.split('.')`）+ `frontend/src/i18n/index.ts::lookup`（同为 `key.split('.')`）

两段式 `id`（如 `copper-lamp.demo-tools`）**含点号**，而 i18n 查表以点号为分隔符且**没有转义机制**。若把完整 `id` 塞进键名，`t("module.copper-lamp.demo-tools.navTitle")` 会被拆成四段，第二段查不到，结果必然回退键名。

**正确做法：显式声明单段 `i18n_namespace`，后端与前端用同一个值（且等于 id 第二段）。**

| 用途 | 取值来源 |
|---|---|
| 唯一标识 | `id` |
| 模块目录名 | `id`（`<modules_dir>/<id>/`，Windows 文件名允许点号） |
| 资产文件名 | `id`（`<id>-<version>-<platform>.cglm`） |
| **语言包挂载名 / `t()` 键前缀** | **`i18n_namespace`** |
| 路由 path | 模块自定（`nav.path`，与 `id` 解耦） |

已核实**无需转义**的两处（切勿画蛇添足）：

1. **设置键 `modules.<id>.enabled`**：设置服务把 key 当作不透明扁平字符串处理，从不 `split('.')`，点号安全。该键由内核拼接，模块侧不参与。
2. **事件桥接的 `.`→`-`**：只对事件名做转换，模块 `id` 不进入事件名。

前端语义补充：`MODULE_LOCALES` 里以 moduleId 作为 **JavaScript 对象键**（`packs[moduleId] = …`），JS 对象键不拆点号，真正会拆点的只有 `t()` 收到的键字符串。**对象键安全，键字符串危险。**

## 十二、「没反应」排查表

契约对不上时，表现几乎都是「界面没有变化」或「报错但看不到原因」。按此表逐项核对。

| 症状 | 最可能的原因 | 核对方法 |
|---|---|---|
| 附加模块未被扫描到 | 目录名不是合法两段式 id | 目录名必须等于 `module.json.id`；非法目录名会被跳过并留 warning |
| 装载失败、状态 `failed` | `init` 或 `start` 返回 `Err`；清单校验不过；helper 找不到 | 看内核日志与 `modules_list` 暴露的错误文本；helper 路径可用 `COPPER_MODULE_HELPER` 显式指定 |
| 插件「能被扫描但不被加载」 | 手工拼函数表导致 `struct_size` / `abi_version` / `module_id` 漂移 | 用 `copper_module_plugin!` 宏；`init` 中调用 `host.validate()` |
| 插件自报 id 与清单不一致 | 宏里的 `id` 与清单 `id` 不同 | `PluginFunctionTable::validate` 会以 `ModuleIdMismatch` 拒绝装载 |
| 左导航没有本模块入口 | 前端入口脚本未在磁盘 / `module.json` 未启用 / `register.js` 未调用宿主桥 | 核对 `modules_frontends` 返回是否含本模块；入口脚本必须经 `window.__COPPER_HOST__.registerModule` 登记 |
| 导航出现但点进去空白 | `nav.path` 与 `routes[].path` 不一致 | 两者逐字相同 |
| 文案显示成键名 | 语言包未注册，或键前缀用了完整 `id` | 键前缀必须是 `module.<i18n_namespace>.*`；命名空间必须等于 id 第二段 |
| 命令调用失败但看不到原因 | 插件只回状态码；前端未拆信封 | 插件把失败装进 `{ok:false, error}` 信封；前端封装拆信封 |
| 命令调用报「命令未找到」 | 命令名与前端传的不一致；或模块未 `start` | 核对 `invoke` 路由与命令解析；未启动时返回 `NotStarted` |
| 事件收不到 | 事件名不在 `events.subscribe` 上界内；或模块未授予 `Events` | 核对清单模式与沙箱授权（见第六节） |
| 事件不补发历史 | 附加模块用 `subscribe_from_now`，**刻意不补发** | 设计如此；需要初始快照就在 `start` 时主动查询 |
| 事件洪峰丢事件 | 队列容量 256，满则丢弃并计数 | 观察 `AddonEventBridge::dropped()`；插件处理过慢会出现 |
| 发布事件报 `event_not_declared` | 事件名不在清单 `events.publish` 上界内 | 补进清单，或改用自证域前缀 `<域>.*` |
| 意图请求报 `intent_unavailable` | 没有模块声明该意图，或转发超时 | 插件据此降级；确认目标模块已 `start` |
| 意图请求报 `intent_failed` | 权限拒绝 / 目标未运行等 | 不属于「稍后重试即可」，需修权限或目标状态 |
| 存储写入报 `storage_quota_exceeded` | 单模块命名空间超过 4 MiB | 模块侧自行控制数据量 |
| 存储读取报 `storage_corrupt` | `storage.json` 损坏 | 内核刻意报错而非静默重置，避免吞数据 |
| `error[E0603]: module ... is private` | 内核 crate 该模块未开放可见性 | 插件**不应**依赖内核 crate；只用 `copper-module-abi` |

## 十三、契约变更纪律

- 插件 ABI 结构（`HostApi` / `PluginFunctionTable` 字段或回调签名）变更必须递增 `plugin_abi::ABI_VERSION`。
- IPC 协议（方法名 / 信封 / 帧格式）变更必须递增 `ipc::PROTOCOL_VERSION`。
- 清单字段语义变更必须递增 `schema_version` 或 `api_version`（`manifest.rs` 装载前比对，不匹配拒绝装载）。
- 已发布的**事件名 / 意图名视为契约**，改名属破坏性变更。
- 模块侧提升 `launcher.min` 属破坏性变更，须在 `CHANGELOG.md` 顶部标注 `BREAKING`。
