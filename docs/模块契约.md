# 模块契约

本文摘录铜内核（`CopperCore`）对附加模块的**硬契约**。所有条目均以 `CopperCore` 真实源码为准，逐条标注出处文件路径，不包含任何推测内容。

> 权威设计文档：仓库根 `D:\CopperGolem\docs\cgl-models.md`（本仓库之外的主仓库文档）。
> 收录侧契约：`D:\CopperGolem\docs\cgl-libs.md`。
> 读法：本文写的「当前」「尚未实现」均指 `CopperCore` 源码的现状，不是本模板的取舍。
>
> **约定**：本文只描述**契约本身**（接口长什么样）。当前阶段一能否通过 path 依赖消费本契约，受内核侧实现缺陷影响——见 [设计](设计.md) 3.1 的 G14（内核 crate 未开放模块可见性）与 G15（依赖链需要 OpenSSL）。现状与阻塞集中在 [设计](设计.md) 承载，本文不重复。

**阅读前必须知道的一件事**：本模板仓库是**附加模块**仓库，不是内核仓库。内核契约由 `CopperCore` 源码单方面定义，模块侧只能对齐，不能臆造。理解偏差的典型表现是「代码编译通过、运行起来没反应」——原因通常是某个契约没对上（见文末排查表）。

## 一、Module trait（模块后端生命周期）

出处：`CopperCore/src-tauri/src/registry/modules.rs`（第 20–32 行）

```rust
pub trait Module: Send + Sync {
    /// 模块唯一标识（如 `home`、`game-download`、`content-download`）。
    fn id(&self) -> &'static str;

    /// 初始化：事件订阅、意图声明、数据库 schema。
    fn init(&self, kernel: &KernelContext) -> Result<(), KernelError>;

    /// 启动：模块开始工作。
    fn start(&self, kernel: &KernelContext) -> Result<(), KernelError>;

    /// 停止：退订、注销意图、释放资源。
    fn stop(&self, kernel: &KernelContext) -> Result<(), KernelError>;
}
```

trait **只有这四个方法**：`id` / `init` / `start` / `stop`。**没有**命令注册方法——命令注册发生在命令层与 `lib.rs` 的 `generate_handler`，不在 trait 上。

装载语义（同文件第 116–166 行）：

| 行为 | 实证 |
|---|---|
| 启动流程 | `boot()` 对每个启用模块执行 `init(...).and_then(|_| start(...))` |
| 失败处理 | 任一环节失败即中止该模块并置 `ModuleState::Failed`，错误文本存入 `errors` 并由 `modules_list` 命令暴露给设置页 |
| 启用开关 | 设置键 `modules.<id>.enabled`，`is_enabled` / `set_enabled`；默认启用（`get_or(..., true)`） |
| 开关生效时机 | 切换后**下次启动生效**，正在运行的模块不受影响（`set_enabled` 注释） |
| 关闭流程 | `shutdown()` 逆序遍历并调用 `stop` |
| 模块来源 | `ModuleOrigin::Builtin` / `ModuleOrigin::Addon`；`register` 默认按 `Builtin`，附加模块应经 `register_with_origin` 显式声明；未登记来源时保守按 `Addon` 处理（`origin_of`） |
| 越权停用态 | `ModuleInfo.suspended` 取自 `kernel.sandbox().is_suspended(id)` |

模板对应文件：`src-tauri/src/module.rs` 是 `Module` 的唯一实现落点。`id()` 必须返回与 `module.json` 的 `id` **完全一致**的字符串（含点号的完整两段式 id）。

## 二、KernelContext 访问器表

出处：`CopperCore/src-tauri/src/state.rs`（第 78–140 行）

模块在 `init` / `start` / `stop` 中拿到 `&KernelContext`，经访问器按需取用能力。

| 访问器 | 返回类型 | 用途 |
|---|---|---|
| `runtime()` | `&tokio::runtime::Handle` | 派生异步任务 |
| `paths()` | `&Arc<Paths>` | 目录体系（含 `modules_dir()` / `logs_dir()` / `db_file()` / `versions_dir()`） |
| `versions_root()` | `std::path::PathBuf` | 当前游戏版本根，按设置 `game.directory` 动态解析 |
| `db()` | `&Arc<DatabaseService>` | SQLite 持久化 |
| `settings()` | `&Arc<SettingsService>` | KV 设置读写 |
| `i18n()` | `&Arc<I18nService>` | 语言包注册与查询 |
| `theme()` | `&Arc<ThemeService>` | 主题快照 |
| `tips()` | `&Arc<TipsService>` | 加载提示（内核通用能力，模块经命令层取用） |
| `download()` | `&Arc<DownloadService>` | 投递内核下载队列 |
| `account()` | `&Arc<AccountService>` | 账户 |
| `updater()` | `&Arc<UpdaterService>` | 更新 |
| `events()` | `&Arc<EventBus>` | 事件总线 |
| `intents()` | `&Arc<IntentRegistry>` | 意图注册表 |
| `modules()` | `&Arc<ModuleRegistry>` | 模块注册表 |

`KernelContext` 本身不持有业务状态，只做聚合，因此可安全共享（`state.rs` 第 3–5 行模块注释）。

## 三、数据库持久化与迁移

出处：`CopperCore/src-tauri/src/services/database.rs`

迁移类型（第 16–21 行）：

```rust
pub struct Migration {
    pub version: u32,
    pub name: &'static str,
    pub sql: &'static str,
}
```

API：

| 方法 | 出处 | 语义 |
|---|---|---|
| `migrate_scope(scope: &str, migrations: &[Migration])` | 第 56 行 | 按 `version` 升序执行未应用项，逐项在事务内提交，失败回滚；已应用记录写入 `schema_migrations(scope, version, name, applied_at)` |
| `schema_version(scope: &str) -> Result<u32, KernelError>` | 第 86 行 | 当前已应用的最高版本（无则 0） |
| `with_conn<T>(f: impl FnOnce(&mut Connection) -> Result<T, KernelError>)` | 第 107 行 | 同步访问连接；**`f` 内不得再调用本服务的锁方法，避免死锁**（源码注释原文） |

`scope` 取值（第 55 行注释）：`"core"`（内核自身）或 `"module:<模块名>"`（模块）。

模块侧实证：`CopperCore/src-tauri/src/modules/content_download/mod.rs:637` 调用 `migrate_scope("module:content-download", &[MIGRATION])`；`CopperCore/src-tauri/src/modules/game_download/mod.rs:64` 调用 `migrate_scope("module:game-download", &[installer::MIGRATION])`。**连字符保留在 scope 文本里**。

### 表名前缀规则

命名约定出处：`services/database.rs` 第 5 行模块注释——「模块表命名空间 `module_<名>_*`」。

实证对照：

| 模块 | scope 文本 | 实际表名 |
|---|---|---|
| 内容下载 | `module:content-download` | `module_content_download_record`（`modules/content_download/mod.rs:385`） |
| 游戏下载 | `module:game-download` | `module_game_download_task`（`modules/game_download/installer.rs:119`） |

规则：**scope 文本用原始完整 id（连字符/点号原样保留），表名把 `.` 与 `-` 全部替换为 `_`**。原因是 scope 只是 `schema_migrations` 表里的一个文本值，不参与 SQL 标识符解析；而表名是 SQLite 标识符，不允许含点号。

两段式 id 的换算：`copper-lamp.demo-tools` → 表前缀 `module_copper_lamp_demo_tools_`，scope 文本仍为 `"module:copper-lamp.demo-tools"`。

模板对应：`src-tauri/src/storage.rs` 定义 `MIGRATION` 常量数组，在 `init` 中调用 `kernel.db().migrate_scope("module:<id>", &MIGRATIONS)?`。**不得绕过迁移直接建表**。

## 四、事件总线

出处：`CopperCore/src-tauri/src/registry/events.rs`

### 订阅与发布

| API | 出处 | 签名 / 语义 |
|---|---|---|
| `subscribe(pattern, handler) -> Subscription` | 第 54 行 | `handler` 为 `impl Fn(&str, &Value) + Send + Sync + 'static`，入参为 `(事件名, 负载)` |
| `unsubscribe(sub: Subscription)` | 第 88 行 | 退订，应在模块 `stop` 中调用 |
| `publish(name: &str, payload: Value)` | 第 97 行 | 同步分发给订阅者 → 入有界重放缓冲 → 桥接前端 |
| `pattern_matches(pattern, name)` | 第 134 行 | 匹配规则见下 |

匹配规则（`pattern_matches` 真实实现）：

- `"*"` 匹配全部事件；
- 以 `.*` 结尾为前缀匹配：`download.*` 匹配 `download.created`；
- 其余为精确匹配。

### 至少一次语义

订阅时会把重放缓冲区内**匹配的历史事件立即补发**（第 73–83 行）。重放缓冲容量 `REPLAY_CAP = 64`（第 16 行），超出后丢弃最旧条目。因此：

- 晚订阅不会漏事件，但**可能收到重复事件**——处理逻辑必须幂等。
- 缓冲是有界的，超出容量的历史事件不会再补发。

### 前端桥接：`.` → `-`

出处：`registry/events.rs` 第 117–123 行。`publish` 时 `app.emit(&name.replace('.', "-"), &payload)`，源码注释原文：「Tauri 事件名不允许 `.`（仅 `[a-zA-Z0-9-/: _]`），桥接前端时统一映射为连字符」。

因此后端事件名与前端监听名成对出现：

| 后端 `publish` | 前端 `listen` |
|---|---|
| `download.status` | `download-status` |
| `version.installed` | `version-installed` |
| `settings.changed` | `settings-changed` |
| `content-download.location` | `content-download-location` |

该转换**只对事件名生效**，模块 `id` 本身不进入事件名（`id` 含点号不影响此处）。

### 已存在的事件名（源码实证）

| 事件名 | 发布方 | 出处 |
|---|---|---|
| `download.created` / `download.progress` / `download.status` | 内核下载服务 | `services/download.rs:33-35` |
| `settings.changed` | 内核设置服务 | `services/settings.rs:93,118` |
| `account.changed` / `account.login.state` | 内核账户服务 | `services/account.rs:205,238,263,417,433` |
| `update.status` | 内核更新服务 | `services/updater.rs:329` |
| `version.installed` / `version.removed` | 游戏下载模块 | `modules/game_download/mod.rs`（发布点见其 installer 与 mod）；实例化订阅见 `modules/home/mod.rs:256-261` |
| `versions.changed` | 开始页模块（游戏目录变更时） | `modules/home/mod.rs:266` |
| `game.launched` | 开始页模块 | `modules/home/launch.rs:287` |
| `content-download.location` | 内容下载模块 | `modules/content_download/mod.rs:526` |
| `game-download.enqueued` / `game-download.installed` / `game-download.failed` / `game-download.cancelled` | 游戏下载模块 | `modules/game_download/installer.rs:294,348,400,453,457,621,625`（前端封装见 `frontend/src/events/index.ts`） |
| `demo-tools.activity` | 本模板示例模块 | 本仓库 `src-tauri/src/service.rs` |

**命名约定**：模块自建事件建议用 `<模块域>.<动名词>`，避免与上表撞名。

## 五、意图注册表

```rust
pub type IntentHandler = Arc<dyn Fn(Value) -> Result<Value, KernelError> + Send + Sync>;
```

处理者是**同步**的；重活应自行 `tokio::spawn`（第 13 行注释原文）。

| API | 出处 | 语义 |

| `declare(intent, module_id, handler)` | 第 33 行 | 声明能力。**同一意图重复声明返回错误**，不静默覆盖（错误文本含「重复声明」） |

## 六、i18n 语言包

出处：`CopperCore/src-tauri/src/services/i18n.rs`

| API | 出处 | 语义 |
|---|---|---|
| `register_module_pack(module_id, locale, pack)` | 第 84 行 | 注册模块语言包；`pack` 必须是 JSON 对象，否则返回 `InvalidArgument`（第 90–94 行） |
| `catalog(locale)` | 第 104 行 | 取完整目录（基准 + 模块语言包） |
| `t(locale, key)` | 第 138 行 | 取单个文案 |
| `lookup(root, key)` | 第 154 行 | **点分路径查询嵌套 JSON**：`for part in key.split('.')` |

### 命名空间规则

模块包挂载为 `module.<register_module_pack 的第一个参数>.<扁平键>`（`catalog` 第 117 行 `module_root.insert(module.clone(), pack.clone())`，第 131 行挂到 `merged["module"]`）。

**该参数必须是 `module.json` 的 `i18n_namespace`（单段），不是完整 `id`。** 原因见下节。

内置模块实证：`modules/home/mod.rs:215` 传 `"home"`，`content-download` / `game-download` 传同名单段值，与 `module.content-download.navTitle` 形态一致。

### 回退链与合并语义

- 回退链：目标语言 → `en-US` → 键名（`t` 第 138–150 行；`FALLBACK_LOCALE = "en-US"`）。
- 合并语义（实证）：第一遍收集目标语言包；第二遍**仅对缺失模块**补 `en-US` 回退包，**不回退覆盖已有目标包**（第 112–127 行）。
- 语言包内容为**扁平键**（非嵌套），与内置模块同构。

### 单一数据源实践

内置模块把语言包物理文件放在前端同模块目录 `frontend/src/modules/<id>/locales/<locale>.json`，后端用 `include_str!` 同源嵌入。实例：`modules/home/mod.rs:217-219` 用 `include_str!("../../../../frontend/src/modules/home/locales/en-US.json")`。

模板同构做法：语言包放 `frontend/src/locales/<locale>.json`，由 `src-tauri/src/module.rs` 的 `include_str!` 引入，**前后端共用同一份文件**。

## 七、两段式 id 与 i18n 命名空间解耦（最容易踩的坑）

出处：`services/i18n.rs::lookup`（`key.split('.')`）+ `frontend/src/i18n/index.ts::lookup`（同为 `key.split('.')`）。

两段式 `id`（如 `copper-lamp.demo-tools`）**含点号**，而 i18n 查表以点号为分隔符，且**没有任何转义机制**。

若把完整 `id` 塞进键名，`t("module.copper-lamp.demo-tools.navTitle")` 会被拆成 `module` / `copper-lamp` / `demo-tools` / `navTitle` 四段，第 2 段 `copper-lamp` 查不到，结果必然回退键名——界面显示 `module.copper-lamp.demo-tools.navTitle` 而不是文案。

**正确做法：显式声明单段 `i18n_namespace`，后端与前端用同一个值。**

| 用途 | 取值来源 | 说明 |
|---|---|---|
| 唯一标识 | `id` | 全局唯一，两段式 `author.module` |
| 模块目录名 | `id` | `paths.modules_dir()/<id>/`，Windows 文件名允许点号 |
| DB scope 文本 | `id` | `migrate_scope("module:<id>", …)` |
| DB 表名前缀 | `id` 派生 | `.` 与 `-` 替换为 `_` |
| 资产文件名 | `id` | `<id>-<version>-<platform>.cglm` |
| **语言包挂载名** | **`i18n_namespace`** | `register_module_pack(<i18n_namespace>, locale, pack)` |
| **`t()` 键前缀** | **`i18n_namespace`** | `module.<i18n_namespace>.<扁平键>` |
| 路由 path | 模块自定 | `nav.path`，与 `id` 解耦 |

后端与前端**必须使用同一个 `i18n_namespace`**。项目历史上已因语言包命名空间前后端不一致出过同类 bug（主仓库 `docs/铜核心/设计.md` 4.5、`docs/模块/开始页/设计.md` 4.5：命名空间不一致导致模块文案整体回退键名）。

### 已核实无需转义的两处（切勿画蛇添足）

1. **设置键 `modules.<id>.enabled`**：`registry/modules.rs:155,165` 用 `format!("modules.{id}.enabled")` 拼键，而 `services/settings.rs` 把 key 当作不透明扁平字符串处理（直接 `cache.get(key)` / `cache.insert(...)` / `SELECT key, value FROM core_settings`），**从不 `split('.')`**。故点号 id 在设置键上安全。该键由内核拼接，模块侧不参与。
2. **事件桥接的 `.`→`-`**：只对事件名做转换，模块 `id` 不进入事件名。不要因为 id 含点号去改事件名规则。

### 前端语义补充

`frontend/src/i18n/index.ts` 的 `MODULE_LOCALES` / `packs` 以 moduleId 作为 **JavaScript 对象键**（`packs[moduleId] = …`）。JS 对象键不拆点号，所以以完整 `id` 作对象键本身不会出错；真正会拆点的只有 `t()` 收到的键字符串。**对象键安全，键字符串危险**。本方案下两者统一走 `i18n_namespace`，但排查问题时不要误改对象键那一侧。

## 八、前端模块注册契约

出处：`CopperCore/frontend/src/modules/registry.ts`

```ts
export interface ModuleNavItem {
  id: string;          // 所属模块 id
  path: string;        // 点击跳转的列表页路径
  titleKey: string;    // 左导航 title / tooltip 的 i18n 键
  icon: Component;     // 导航图标组件（来自 @lucide/vue）
}

export interface ModuleFrontend {
  id: string;
  nav: ModuleNavItem;
  routes: RouteRecordRaw[];
}

export function registerModule(module: ModuleFrontend): void;
```

该接口的注释明确将其定位为「内核模块前端注册扩展点」，**不是公开稳定 API**。

硬约定（源码实证）：

1. **每个模块恰好调用一次** `registerModule({ id, nav, routes })`；重复 `id` 直接 `throw`（第 40–42 行），不静默覆盖。
2. **注册顺序即左导航顺序**（`navOrder` 数组，第 36 行）；内置模块的顺序由 `frontend/src/modules/index.ts` 的 `import` 顺序决定。
3. `nav.path` 指向模块列表页；`titleKey` 走 i18n，键前缀为 `module.<i18n_namespace>.`。
4. `routes` 为 vue-router 记录，组件推荐懒加载 `() => import("./ModulePage.vue")`。
5. 路由 `meta.titleKey` 驱动标题栏标题（内核 Shell 读取）。实证：`modules/content-download/register.ts` 的 `meta: { titleKey: "module.content-download.listTitle" }`。
6. 模块间**不互相依赖**，只经注册表与内核 Shell 交互。
7. 其余访问器：`getModuleFrontends()` / `getModuleNav()` / `getModuleRoutes()` 供内核 Shell 收集（第 48–59 行）。

## 九、命令层与错误类型

出处：`CopperCore/src-tauri/src/error.rs`、`CopperCore/src-tauri/src/lib.rs`、`CopperCore/frontend/src/api/core.ts`

```rust
pub struct CommandError {
    pub kind: String,
    pub message: String,
}

pub type CommandResult<T> = Result<T, CommandError>;
```

- `CommandError` 以 **snake_case** 序列化（`#[serde(rename_all = "snake_case")]`，`error.rs:58`）。
- `kind` 由 `KernelError` 变体映射（`CommandError::from_kernel`，`error.rs:64-86`），全部取值：`invalid_argument` / `io` / `database` / `serde` / `http` / `download` / `keyring` / `event_bus` / `intent` / `module` / `account` / `updater` / `config`。
- 命令经 `#[tauri::command]` 定义，返回 `CommandResult<T>`。
- **命令必须在 `lib.rs` 的 `tauri::generate_handler![...]` 中注册**（`lib.rs:122-200`），该列表**当前为静态硬编码**。
- 前端统一经 `frontend/src/api/core.ts` 的 `call<T>(cmd, args)` 调用；出错时归一化为 `KernelApiError`（携带 `kind` 与 `message`）；`invoke` 自身失败时兜底为 `kind: "invoke"`。

模块侧要求：**禁止裸调 `invoke`**，一律经 `api/core.ts` 的 `call` 或模块自己的 `api.ts` 封装（本仓库为 `frontend/src/api.ts`）。

## 十、沙箱权限枚举（当前仅意图路径生效）

出处：`CopperCore/src-tauri/src/registry/sandbox.rs`

枚举与字符串取值（第 25–72 行）：

| 变体 | 字符串取值 |
|---|---|
| `FileSystem` | `file_system` |
| `Network` | `network` |
| `Database` | `database` |
| `Settings` | `settings` |
| `Ui` | `ui` |
| `Events` | `events` |
| `Intents` | `intents` |
| `SpawnProcess` | `spawn_process` |
| `Notification` | `notification` |

已落地的判定能力（同文件）：`grant`（登记授权，含模块目录）、`knows`、`is_allowed`、`enforce`（越权留痕 + 超限强制停用）、`enforce_path`（拒绝相对路径、规范化后比较、按路径组件比较）、`is_suspended`、`grants`、`revoke_permission` / `restore_permission`（用户只能收紧不能提权）。`module_dir(paths, module_id)` 会在授权时创建 `<data_dir>/modules/<id>` 并返回规范化路径。

**本表与 `module.json` 的 `permissions` 字段不是同一套枚举。** `module.json.permissions` 用的是收录侧 9 项细粒度枚举（`filesystem:read` / `filesystem:write` / `filesystem:game-dir` / `network` / `process:spawn` / `download:enqueue` / `settings:write` / `intents:request` / `account:read`，权威定义见主仓库 `docs/cgl-libs.md` 2.3.6 与 `docs/cgl-models.md` 2.4）。沙箱枚举是内核内部的执行侧模型，两者之间**目前没有任何换算代码**——这属于阶段二装载器落地时的工作。

沙箱当前**无调用方**：已接入意图注册表（`lib.rs:90` 的 `intents.bind_sandbox(...)`）并经 `sandbox_grant` 命令登记，但由于没有附加模块装载器，运行期尚无真正的附加模块流经该路径。

## 十一、明确标注为未实现的能力（阶段二，内核侧）

以下能力**在 `CopperCore` 当前源码中不存在**。模块侧不得假设它们可用，也不得在文档或代码里写成已实现。

| 能力 | 现状 | 对开发者的实际影响 |
|---|---|---|
| 附加模块动态加载 | `ModuleRegistry` 只有 `register` / `register_with_origin` + `boot()`，没有从磁盘装载的代码路径；装载源是 `lib.rs` 里的静态 `register` 调用 | 模块只能以源码依赖形态编译进内核；本模板产出的 `.cglm` 目前不进入用户一键安装链路 |
| 子进程托管与 IPC | 沙箱的**权限判定语义**已落地，但**受管控子进程的拉起、IPC 传输未实现** | 「附加模块跑在独立进程」这一物理隔离尚未生效；模块代码当前不存在独立进程可依附 |
| 运行期前端包装配 | `frontend/src/i18n/index.ts` 的 `MODULE_LOCALES` 硬编码内置三模块 import；`frontend/src/modules/index.ts` 用静态 `import` 决定顺序 | 附加模块前端无法在运行期注册；本模板 `register.ts` 只能经相对路径被内核静态引入 |
| 语言包运行期注册（前端侧） | 后端 `register_module_pack` 已可用，但前端本地兜底映射是静态的 | 内核 catalog 可用时模块文案能正确显示；内核不可用时前端无本地兜底包 |
| 命令动态注册 | `lib.rs` 的 `generate_handler![...]` 是静态列表 | 模块命令不在列表内时，调用会以「命令未找到」失败。本仓库 `frontend/src/api.ts` 把这类失败归一化为 `not_registered` 并如实展示 |
| 模块签名与来源校验 | 内核无任何签名校验代码 | 未收录模块的「未审核」标识无法由签名支撑，只能靠 UI 明示 |
| 手动导入命令 | `commands/modules.rs` 已有沙箱命令，但 `modules_import_local` / `modules_import_archive` / `modules_dev_reload` / `modules_dev_log` / `modules_import_list` **均未实现** | `npm run import:dev` 只能直接写文件系统，不能调用内核命令 |

补充说明：`ModuleInfo.is_builtin` **此前恒为 `true`（硬编码）的问题已修复**——`registry/modules.rs` 新增 `ModuleOrigin`（`Builtin` / `Addon`）与 `register_with_origin`，`list()` 返回真实 `is_builtin` 与 `suspended`。若在旧资料里看到「`is_builtin` 恒为 true」，那是过期信息。

## 十二、「没反应」排查表

契约对不上时，表现几乎都是「界面没有变化」而不是报错。按此表逐项核对。

| 症状 | 最可能的原因 | 核对方法 |
|---|---|---|
| 左导航没有本模块入口 | 前端 `register.ts` 未被内核引入；或 `registerModule` 未执行 | 检查 `frontend/src/modules/index.ts` 是否 import 了本模块的 `register.ts`（阶段一必须静态引入） |
| 导航出现但点进去空白 | `nav.path` 与 `routes[].path` 不一致 | 两者必须逐字相同（本模板为 `/demo-tools`） |
| 文案显示成 `module.demo-tools.title` 这样的键名 | 语言包未注册；或键前缀用了完整 `id` | 后端 `register_module_pack` 的第一个参数必须是 `i18n_namespace`（`demo-tools`）；前端键必须是 `module.demo-tools.<扁平键>` |
| 部分文案正常、部分回退键名 | `zh-CN` 与 `en-US` 键集不一致，或缺 `en-US` 兜底 | `npm run schema:check` 检查键集一致 |
| 模块没有出现 | 模块未注册（`id()` 返回值与注册名不符） | `ModuleRegistry::list()` 按注册顺序返回；`id()` 必须与 `module.json.id` 逐字一致 |
| 模块出现在设置页但状态是 `failed` | `init` 或 `start` 返回了 `Err` | `boot()` 把错误文本存入 `errors`，经 `modules_list` 命令暴露；设置页模块 Tab 可见 |
| 改代码后重启仍无变化 | 模块被停用；或启用开关按 `modules.<id>.enabled` 读取 | 设置页模块 Tab 的启用开关；切换后**下次启动生效** |
| 命令调用报「命令未找到」 | 命令未进入 `lib.rs` 的 `generate_handler![...]` | 阶段一静态链路：需要把命令加入内核的静态列表；本仓库 `api.ts` 会把该失败归类为 `not_registered` |
| 后端发了事件，前端没收到 | 事件名中的 `.` 未在前端换成 `-` | 后端 `download.status` → 前端 `listen("download-status")` |
| 事件处理被重复触发 | 事件总线是**至少一次**语义，订阅时会补发重放缓冲内的历史事件 | 处理逻辑必须幂等；本模板 `useModuleState.ts` 用 `kind + at + message` 去重 |
| 模块 A 的文案覆盖了模块 B | 两个模块用了同一个 `i18n_namespace` | 命名空间全仓库唯一，由 CI 与提审校验 |
| 表不存在 / SQL 报错 | 迁移未执行；或表名里留了点号/连字符 | `init` 中必须有 `migrate_scope("module:<id>", &MIGRATIONS)`；表名把 `.` 与 `-` 换成 `_` |
| 设置项读不到 | 设置键拼错；或误以为点号 id 需要转义 | 设置键是**不透明扁平字符串**，点号安全；内核侧键形如 `modules.<id>.enabled` |

## 十三、契约变更纪律

- 内核每次改动 `Module` trait 签名、`KernelContext` 访问器、事件/意图语义、`registerModule` 签名时，必须递增 `api_version`（主仓库 `docs/cgl-models.md` 3.2）。
- 内核在装载前比对 `api_version`，不匹配则拒绝装载并给出可读原因（**该比对逻辑随装载器一并属于阶段二未实现项**）。
- 已发布的事件名 / 意图名视为契约，改名属破坏性变更，须走 `api_version` 递增流程。
- 模块侧提升 `launcher.min` 属破坏性变更，须在 `CHANGELOG.md` 顶部标注 `BREAKING`。
