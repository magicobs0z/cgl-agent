# 发布流程

本文定义模块的版本号规则、tag 规范、Release 内容、提审 bot 链路、幂等与回滚。链路对齐主仓库 `docs/cgl-models.md` 2.9 / 2.10 与 `docs/cgl-libs.md` 2.8。

> 开发流程见 [开发指南](开发指南.md)；契约细节见 [模块契约](模块契约.md)。

---

## 一、版本号规则

版本号形态为 `x.x.x`（major.minor.patch），规则对齐主仓库 `AGENTS.md`：

| 位 | 含义 | 变更时机 |
|---|---|---|
| 第 1 位 | 保持 `0` | 项目尚处早期阶段，不递增 |
| 第 2 位 | 大版本 | 有重要更新时递增 |
| 第 3 位 | 小版本 | 修复 bug 或小改动时递增 |

**模块作者不得自行变更版本号。** 版本号变更须由维护者下达指令后执行，不允许在普通 PR 里顺手改。原因有三：

1. 版本号是发布链路的触发键——tag、Release 资产名、`cgl-libs` 条目 `version` 四处必须一致，任意一处被单独改动都会让链路断裂。
2. 已收录版本的 `cgl-libs` 条目不可回改（条目字段单向派生自 manifest，见主仓库 `docs/cgl-models.md` 2.10.1），错版本要发新版本纠正。
3. 版本号与 `CHANGELOG.md`、README 的现状描述联动，需要一并更新。

### 版本号的一致性要求

以下四处必须**逐字一致**，由 CI 与提审校验：

| 位置 | 内容 |
|---|---|
| `module.json` 的 `version` | `0.1.0` |
| git tag | `v0.1.0`（前缀 `v`，去掉后与上者相同） |
| `CHANGELOG.md` 的版本段标题 | `## [0.1.0] - <日期>` |
| `cgl-libs` 条目的 `version` | 由 bot 从 manifest 直取，等于 Release tag 去掉前缀 |

CI 侧对应步骤：`module-package.yml` 的 `verify` 作业执行 `node scripts/validate-manifest.mjs --expect-version "${GITHUB_REF_NAME#v}"`，不一致直接失败。

### 更新顺序

维护者下达版本指令后，按此顺序执行：

1. 改 `module.json` 的 `version`；
2. 更新 `CHANGELOG.md`（把 `Unreleased` 段的内容归入新版本段，写清相对上一版本的可见变化）；
3. 更新 `README.md` 中过时的现状描述（平台、内核版本要求、权限、功能列表）；
4. 维护者确认通过后打 tag 并提交。

## 二、tag 规范

| 项 | 规范 |
|---|---|
| tag 名 | `v<version>`，如 `v0.1.0` |
| 打 tag 的人 | 维护者（模块作者不得自行打 tag 触发发布） |
| 触发效果 | `push: tags: ['v*']` 触发 `module-package.yml` |
| 校验 | tag 去掉 `v` 前缀后必须等于 `module.json.version` |

`module-package.yml` 也支持手动触发（`workflow_dispatch`），需要填写与 `module.json.version` 一致的 `version` 输入。

## 三、Release 构建与资产

链路：`verify`（校验）→ `package`（按平台矩阵构建并打包）→ `publish`（上传到 Release）。

### 产物

每个平台产出两个文件，**成对存在**：

| 文件 | 内容 |
|---|---|
| `<id>-<version>-<platform>.cglm` | 模块包（zip 容器，见下） |
| `<id>-<version>-<platform>.cglm.sha256` | 单行小写十六进制 + 两空格 + 文件名 |

示例：`copper-lamp.demo-tools-0.1.0-windows-x86_64.cglm` 与 `copper-lamp.demo-tools-0.1.0-windows-x86_64.cglm.sha256`。

### 包内布局（冻结契约）

```
module.json          清单（与仓库根同名文件一致，随包分发）
manifest.sha256      包内逐文件校验清单（逐文件 sha256）
icon.svg             图标（从 assets/ 复制到包根，便于列表预览快速读取）
backend/<产物>       后端产物（Windows 为 .dll）
frontend/**          前端产物（register.js + assets）
runtime/<entry>      受监管运行时入口（清单声明 runtime 时必需）
LICENSE              许可文件（合规要求，随包分发）
```

`runtime/` 是 `npm run build:runtime` 的产物（已在 `.gitignore` 中，不入库），打包器在清单声明 `runtime` 时**强制要求**它存在，并校验 `runtime.entry` 指向的文件确实在包内——缺了会在打包期失败，而不是等内核装载时才拒绝。`runtime.entry` 之外的路径一律以 `runtime/` 前缀入包，与内核 `RUNTIME_DIR` 约束一致。

`.cglm` 就是 zip 容器，文件名承担类型标识作用（与 `cgl-libs` 的 `assets[].url` 及内核缓存路径 `<id>-<version>.cglm` 一致）。

### Release 检查清单

发布前逐项确认：

- [ ] `module.json.version` 与 tag 一致。
- [ ] `CHANGELOG.md` 有对应版本段，写清了相对上一版本的可见变化。
- [ ] `platforms` 中的每个平台都有对应产物——`platforms` 是承诺而非描述，缺产物即提审失败。
- [ ] 两个文件的 `.sha256` 都已生成且校验通过。
- [ ] `LICENSE` 文件存在，且与 `module.json.license` 的 SPDX 标识一致。
- [ ] 声明了 `runtime` 的模块：`runtime/<entry>` 已由 `npm run build:runtime` 产出并随包分发（打包期会强制校验）。
- [ ] `THIRD_PARTY_NOTICES.md` 已登记随包分发的全部第三方组件（**本模板不分发任何第三方二进制**）。
- [ ] Release 不是预发布（`channel` 由 `cgl-libs` CI 依据 Release 是否为预发布判定）。

### 构建来源纪律

产物由 CI 构建，**禁止本地构建后手工上传**——避免来源不可追溯。打包 workflow 固定 Rust 工具链与 Node 版本，保证可复现。

## 四、提审 bot

触发条件：Release 正式发布（`release: types: [published]`）。

链路：

```
Release 发布
  -> 校验 Release 资产齐全（.cglm 与 .sha256 成对）
  -> 生成 cgl-libs 条目 JSON
  -> 检出 cgl-libs，写入对应分片
  -> 开 PR（幂等）
  -> 管理员审核合并 -> 进入模块列表
```

### 分支名

固定为 `module/<模块仓库名>`。同一模块重复发布**复用同一分支**，避免 PR 堆积。

### 条目写入位置

`cgl-libs` 的模块元数据按首字母范围分片，bot 把条目并入对应分片：

```
cgl-libs/
├─ modules/_index.json      分片清单（列表页拉取入口）
├─ modules/by-id.json       id -> 分片路径映射
└─ modules/<分片名>.json     分片文件，内含模块条目数组
```

`index.json` / `modules/_index.json` / `modules/by-id.json` 由 `cgl-libs` CI 重新生成，**bot 不得修改这三个文件**。条目字段定义见主仓库 `docs/cgl-libs.md` 2.3.2，字段映射见 2.3.6。

### 幂等四条

1. 若目标分支已存在 PR，则**更新该 PR** 而非新建。
2. 写入前按 `id` 在目标分片的 `modules[]` 中定位该模块条目，存在则**整体替换该条目对象**。
3. 相同 `(id, version)` 重复触发时，若内容比对无差异则**不产生提交**。
4. 生成条目之前先校验 `module.json.version` 与 tag 一致，不一致直接失败。

### 防投毒

提审**只使用 Release 中已上传的资产 URL 与 `sha256`**；bot 不自行构建、不改写产物、不"顺手修一下"校验值。任何 bot 无法从 manifest 与 Release 唯一确定的字段，一律**失败而非猜测**。

### 令牌最小化

- bot 对自身仓库只需 `contents: read`。
- 写 `cgl-libs` 的权限经 `CGL_LIBS_TOKEN` 提供，须为**细粒度 PAT 且仅授权目标仓库**。
- 令牌存于仓库 Secret，禁止在 workflow 中回显。

### bot 的责任边界

bot **只填**：`id`、`i18n_namespace`、`display_name`、`summary`、`author.name`、`author.contact`、`repo`、`license`、`version`、`min_launcher`、`max_launcher`、`api_version`、`platforms`、`assets`、`permissions`、`changelog`、`published_at`。

bot **必须留给维护者**：`channel`、`status`（bot 一律填 `pending`）、`yanked`（bot 一律填 `false`）、`yank_reason`（bot 填 `null`）、`author.verified`（bot 填 `false`）。

由 `cgl-libs` CI 生成：`icon.*`、`permissions_derived`。

> `permissions_derived` 是只读的三布尔摘要，由 `permissions` 派生：`network` ← 含 `network`；`spawn_process` ← 含 `process:spawn`；`write_outside_module_dir` ← 含 `filesystem:game-dir` 或 `settings:write`。模块作者只写细粒度枚举，不写摘要。

### 提交信息规范

头英文、内容中文（对齐主仓库 `AGENTS.md`）。示例头：`Add module entry: copper-lamp.demo-tools v0.1.0`。

## 五、失败处理

以下情况一律 **fail**，不生成半成品条目：

| 情况 | 处理 |
|---|---|
| 资产缺失（`.cglm` 与 `.sha256` 不成对） | 提审失败 |
| 校验值不一致 | 提审失败 |
| `module.json` 未过 schema | 提审失败 |
| `module.json.version` 与 tag 不符 | 提审失败 |
| `author.url` 与 `author.email` 皆缺 | 提审失败（收录红线第 5 条） |
| `i18n_namespace` 与既有条目冲突 | 提审失败（命名空间重复会导致两个模块文案互相覆盖） |
| 某平台声明了但 Release 无对应产物 | 提审失败 |

排查顺序：先看 Release 资产是否齐全成对，再看 CI 的结构化摘要（哪一条目、哪一字段、期望值 vs 实际值），最后核对 manifest 与 tag 的一致性。

## 六、回滚

### 发布失败（构建或上传阶段）

Release 尚未正式发布时直接删除该 Release 与 tag，修复后重新打 tag。此阶段没有对外影响。

### 已发布但内容有误

**不要删除或覆盖已发布的 Release 资产**——`cgl-libs` 条目中的 `assets[].url` 与 `sha256` 已锚定该资产，覆盖会让已安装用户与条目校验不一致。

正确做法：发一个新版本（递增第 3 位），在 `CHANGELOG.md` 中写明修复内容。新版本的提审 PR 会按分支幂等规则更新同一 PR。

### 需要紧急撤回（yank）

安全问题时走 **yank 快速通道**：

1. 在 `cgl-libs` 提 PR 把对应条目的 `yanked` 置为 `true`，并填写 `yank_reason`。
2. yank 类 PR 允许一名维护者在 CI 的资产校验步骤失败时跳过该步骤直接合并（安全事件不宜被网络问题阻塞），但必须在 PR 描述中记录原因。
3. `yank` 状态经 `index.json` 的 3600s TTL 生效，最坏延迟 1 小时。
4. 客户端对 `yanked: true` 的条目：已安装用户看到警告与卸载引导，未安装用户按钮置灰。

**yank 的边界必须清楚**：yank 只阻止新安装，**不会卸载已安装的模块**。这正是收录侧在模块隔离能力落地前关闭第三方投递的原因——没有强制隔离时，一旦模块被装进用户机器，撤回手段就只剩事后提示。

### 版本回退

`cgl-libs` 的任何一次发布都能通过 revert 单次 merge commit 回到上一状态。模块侧不要把「回退」理解为「把 tag 挪回去」——tag 不可变，回退靠发新版本。

## 七、当前阶段说明（诚实标注）

本模板的发布链路**当前能跑通**：CI 校验、按平台打包、生成 `.sha256`、上传 Release、生成 `cgl-libs` 条目并开 PR，这些都不依赖动态加载能力。

**但面向终端用户的一键安装尚未生效**，原因在**内核侧**，不在本模板：

| 未实现项 | 现状 | 影响 |
|---|---|---|
| 附加模块动态加载 | 内核 `ModuleRegistry` 无磁盘装载路径 | `.cglm` 不能被杀软式地"装上就能用" |
| 子进程托管与 IPC | 权限判定语义已落地，物理隔离未落地 | 附加模块无独立进程可依附 |
| 模块装载器 / 签名校验 | 未实现 | `api_version` 比对、来源校验无执行点 |

因此当前的产物定位是**开发期分发**（源码包 + 校验值，供开发者自行编译），不是终端用户的一键安装包。包结构已按阶段二的最终形态定义，届时不需要改契约。

收录侧的对应策略：**第三方投递在隔离能力落地前关闭**，`cgl-libs` 只接受 `author.verified: true` 的官方条目。详见主仓库 `docs/cgl-libs.md` 1.5 与 1.7。
