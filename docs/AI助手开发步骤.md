# AI 助手开发步骤

## 需求

本文是 `cgl-agent` 模块仓库的可执行开发清单，目标是基于 Pi Agent Core 与 Pi AI 完成 CopperGolem AI 助手首期功能，并按本仓库发布流程提交至官方模块列表，使用户能够从启动器模块列表安装。范围仅包含本模块仓库；不把修改 CopperCore 作为默认工作，也不把“源码中存在某个接口”当成端到端链路已验证。

首期功能：通用问答、启动器问题诊断、provider/model 配置、流式回答、取消与错误反馈。Pi 负责 Agent 循环和模型调用；本模块负责 CopperGolem UI、少量系统提示词、Pi 与模块契约的适配，以及经批准的诊断工具。不得加入任意命令执行、开放文件系统、代码写入或未批准的工具。

总体职责见[设计](设计.md)，模块通用开发和契约见[开发指南](开发指南.md)与[模块契约](模块契约.md)，打包提审见[发布流程](发布流程.md)。本文件补充 AI 模块的实际实施顺序与验收方法，不替代上述契约。

## 架构

### 执行纪律

- 按下列顺序推进；前置验收未通过时暂停后续依赖工作，不用模拟结果或临时硬编码绕过。
- 业务代码只提交到 `cgl-agent`。核对 CopperCore 契约时只读；若发现必须新增内核能力，记录阻塞所需的精确 API/行为，不在本计划中改内核，也不先实现依赖它的功能。
- 对同进程 Rust 动态库、Pi 的 JavaScript/TypeScript SDK、凭证存储和前端动态装配，均以当前源码与实际运行验证为准。CopperCore 当前可见 `ModuleLoader`、`DylibBackend`、`module_invoke`、附加模块前端资源服务和模块安装命令，但这些符号的存在本身不能证明 Pi runtime、密钥访问和用户一键安装全链路已经满足本模块需求。
- 不自行更改模块版本号、tag 或发布资产。发布版本由维护者指令确定，规则见[发布流程](发布流程.md)。

### 0. 开工基线与范围锁定

1. 在 `D:\CopperGolem\cgl-agent` 检查工作区改动，确认已有用户修改；后续只编辑本模块所需文件，不覆盖与本任务无关的改动。
2. 检查 `module.json`、`package.json`、`src-tauri/Cargo.toml`、`frontend/src/`、`src-tauri/src/`、`tests/`、`.github/workflows/`，记录现有 ID、语言命名空间、平台、crate 产物名、构建脚本和发布矩阵。
3. 执行基线检查：

   ```powershell
   npm test
   npm run schema:check
   npm run build:frontend
   cargo test --manifest-path src-tauri/Cargo.toml
   ```

   若本机 Rust 链接需要 OpenSSL，按[开发指南](开发指南.md)配置 CopperCore 提供的环境后重跑，不得把环境错误记成测试通过。
4. 将示例模块身份改为 AI 模块的正式身份前，先确认官方列表要求的唯一 `id`、唯一 `i18n_namespace`、作者联系方式、许可、支持平台和权限。不得沿用 `copper-lamp.demo-tools`、`demo-tools` 或示例描述发布。

**验收**：基线命令结果已记录；目标模块身份及首期功能范围明确；未改版本号；不相关工作区改动保持原样。

### 1. 验证可安装、可运行和安全凭证路径

这一步是硬门禁。先用最小验证代码或现有模块样例检查通路，不先开发完整聊天 UI。

1. 逐项对照本模块使用的主内核源码：
   - 清单与兼容门禁：`CopperCore/src-tauri/src/registry/manifest.rs`、`registry/loader.rs`。
   - 模块动态库入口：`registry/dylib_backend.rs`、`registry/module_entry.rs`。
   - 模块命令转发：`commands/modules.rs` 中 `module_invoke` 与 `Module::invoke`。
   - 前端安装后资源发现及路由/导航装配：`registry/frontend.rs`、`commands/modules.rs`、`frontend/src/modules/registry.ts` 及其真实调用方。
   - 官方目录安装：`registry/install.rs`、`services/registry.rs`、前端模块列表安装调用链。
   - 模块安全权限与凭证：`registry/sandbox.rs`、`platform/secret.rs`、`platform/mod.rs`；确认附加模块究竟能否以获准方式存取专属凭证，不能仅凭 `KernelContext::backends().secret()` 存在就判定可用。
2. 用本仓库的 `npm run import:dev` 将开发构建导入启动器，确认前端页面确实出现在模块界面；按启动日志确认 Rust 动态库已加载，模块清单 ID 与二进制 `Module::id()` 完全一致，模块 API 请求实际到达 `invoke`。记录宿主版本、平台和复现步骤。
3. 做一个单独的运行时验证：将 Pi Agent Core 与 Pi AI 的实际锁定版本加入本仓库依赖，验证目标运行时能加载所需包、provider 能发出一次真实请求、流式事件能被消费、取消可中断请求，并能打入发布包。查明其许可证和传递依赖，锁定依赖版本与 lockfile。禁止在 Rust 中把 npm 包当作 Rust crate；禁止把 API Key 写入 Vue 状态、localStorage、普通设置、会话或日志。
4. 在启动器中验证设置页入口及 API Key 保存/读取契约。普通 provider/model/base URL 等非敏感字段可走普通设置；API Key 必须经内核确认过的安全凭证路径保存，读取时仅在可信执行侧按需使用。对保存、读取、替换、删除、错误平台、无凭证和重启后读取逐一实测。Android 等不支持安全存储的平台必须明确禁用凭证配置/问答并给出说明，不能退化为明文。
5. 如 runtime 只能在 WebView 中运行，先验证密钥边界是否满足要求；如需要模块另启子进程、IPC 或新的密钥命令，而内核当前没有受支持的契约，则将它记为阻塞并停止依赖该契约的实施。不得通过新增任意进程权限或模块私有旁路假装解决。
6. 验证模块列表的一键安装链路：在干净的启动器用户数据目录中，从官方模块列表选择模块，完成下载、校验、安装、重启后加载、前端页面显示、命令调用与卸载。另测损坏包、平台不匹配、内核版本不匹配、重复安装和网络失败。记录一键安装实际生效与否；只看到模块出现在目录或列表，不算成功。

**验收**：形成可复现的目标平台运行时方案；设置/密钥/模型请求闭环通过；开发导入与官方列表一键安装均有实机验证记录。若任何一项依赖内核缺口，停止对应实现，给出缺少的精确契约与失败证据，等待内核侧另行决策，不扩大本轮修改范围。

### 2. 建立正式模块骨架和前端入口

1. 更新 `module.json`：采用已确认的正式模块 `id`、单段 `i18n_namespace`、中英文名称与说明、作者联系方式、SPDX 许可、平台、启动器兼容范围、API 版本、Pi 模块后端入口、前端 `dist/register.js`、图标和最小权限集合。字段必须符合仓库 schema；平台字段必须与实际 CI 产物逐一对应。
2. 更新 `src-tauri/Cargo.toml` 与 `src-tauri/src/module.rs`：将包名、动态库产物名、模块类型和 `module.json` 一致；实现正确的生命周期、正式 ID、版本及 `invoke` 命令分发。生命周期启动/停止要成对清理订阅、任务和运行态资源；重复启动、停止和失败都不得泄漏任务或伪报成功。
3. 在 `frontend/src/register.ts` 注册正式导航和路由；页面放在职责清晰的 Vue 文件中，复用现有布局模式。所有文案进入 `frontend/src/locales/zh-CN.json` 与 `en-US.json`，使用单段命名空间，键集完全一致。样式只用 CopperCore `--copper-*` 主题令牌，图标使用已安装的 `@lucide/vue`。
4. 设置入口按已经验证的启动器契约接入；不自行改 CopperCore 设置页面。若现有设置 API 不支持第三方模块设置入口，则记录阻塞，不造一套看似集成的独立设置页。
5. 清除页面、包名、README、测试和清单中的 Demo 示例文案。保持 `module.json`、Rust manifest 反序列化、前端注册 ID、命令前缀和 i18n namespace 一致。

**验收**：`npm run schema:check`、`npm run build:frontend`、后端 `cargo test` 通过；启动器显示正式模块名称及导航；无示例 ID/文案残留；设置实际落入启动器已验证的设置入口。

### 3. 实现 Pi 最小问答纵向链路

按“设置与凭证 → 后端请求 → 事件/流式响应 → 页面”的顺序实施，先只支持一个已验证 provider/model，闭环后再扩展 provider 列表。

1. 在 `frontend/src/api.ts` 定义类型化模块命令调用；Rust 命令集中在 `src-tauri/src/commands.rs`，只做参数反序列化、权限/状态检查、业务调用与结果映射；Pi 初始化和消息处理放独立 service 文件，避免塞进命令处理器。
2. 在 `module.json` 权限中只添加真实需要的枚举。若模型联网由 Pi runtime 执行，确认联网行为确实受清单权限约束，并在 README 权限说明中逐项说明；禁止因“可能用到”而申请进程、文件或游戏目录权限。
3. 根据第 1 阶段验证过的承载方式，在 service 层创建 Pi agent/runtime，注入最少系统提示词：说明 CopperGolem 助手身份、回答边界、诊断信息不确定性和不得声称执行了未执行操作。由 Pi AI 负责 provider/model 调用，不复制 Agent loop。
4. 提供会话发送、增量事件、完成、取消和错误五类明确状态。每个请求使用可区分的 request/session 标识；后端增量事件映射到内核支持的事件通道，前端 API/composable 负责订阅并在组件卸载时取消监听。事件载荷采用可校验的序列化类型，不将 provider 响应对象或凭证原样透出。
5. 页面覆盖空会话、输入中、流式输出、取消中、完成、无 API Key、配置错误、网络错误、provider 限流和 runtime 不可用状态。取消后不得继续更新旧会话；重复提交、窗口卸载和模块 stop 都应中止或清理对应任务。
6. 为 API Key 增加专门的保存、读取和删除操作，仅通过已验证安全存储契约处理；输入框默认遮蔽，UI 状态不得保留可序列化明文。确认日志、错误栈、事件、测试快照及分析信息不含密钥、认证头或完整请求配置。
7. 会话持久化先按设计文档已确认的策略执行；若策略尚未批准，首版仅做明确的内存会话，不擅自落库。若持久化已确认，使用模块数据库迁移，保存前过滤凭证和敏感诊断数据，并实现删除会话与数据迁移测试。

**验收**：使用测试凭证完成至少一次真实 provider 问答，前端收到多段流式内容；取消、错误和无密钥状态符合约定；从磁盘、普通设置、数据库、日志、事件载荷和打包文件搜索不到测试密钥；模块卸载/重启无残留任务。

### 4. 定义并实现启动器诊断工具

工具清单不得由实现者自行扩张。先将每项候选工具提交为可审阅的接口表，确认后才写代码：名称和用途、只读/副作用、输入 schema、数据源、最少权限、是否联网/外传、敏感字段过滤、失败语义、用户确认要求、可取消性。

1. 首期优先只读诊断。未获批准的工具不可注册到 Pi，不能让模型通过自由文本拼出任意命令、路径或模块命令。
2. 在 `src-tauri/src/` 的工具适配层定义固定工具集合和 JSON schema；每次调用先做结构、长度、枚举及资源 ID 校验，再调用已确认的内核公开命令/意图。拒绝未知字段或越界输入；不得直接读取 CopperCore 私有服务状态。
3. 将每个 MCP 工具转换为 Pi Agent Core 所需的工具定义和执行回调。适配层只做 schema/结果/错误映射，不实现通用 MCP 平台或另一套 Agent 工具框架。若 MCP server/transport 尚无确定可运行的实现或契约，不得仅把普通函数改名为 MCP；先停在接口门禁，确认真实 MCP 传输和生命周期后再继续。
4. 工具结果返回结构化数据并做敏感字段筛除、大小限制和用户可读错误映射；记录工具调用开始、成功、拒绝、超时和取消状态，但不记录用户令牌、API Key 或不必要的原始诊断数据。
5. 对将来获准的副作用工具，先定义明确的前端确认、取消与失败回滚语义；首期不实现未批准的副作用工具。
6. 为每个工具编写测试：合法输入、缺字段、错误类型、超长输入、越权资源、未知工具、内核错误、取消、敏感字段过滤，以及 Pi 收到的结果形状。

**验收**：已批准工具表与实际注册表完全相同；未批准工具无法由模型调用；所有工具均有真实输入校验和错误测试；工具使用的权限与 README、`module.json` 一致。

### 5. 完成会话、可靠性与产品化 UI

1. 补齐 `frontend/src/` 的会话 composable 与拆分组件：消息列表、消息项、输入框、工具状态、错误提示、设置入口。组件只负责展示/交互，异步状态归 composable，后端业务归 service。
2. 定义消息状态迁移与幂等规则：请求启动后只接收匹配 request ID 的事件；完成、失败或取消后终止该 ID 的更新；切换会话或页面卸载按约定取消。流式高频更新做节流/批量合并，避免整段消息列表反复重绘。
3. 若已批准会话持久化，完成迁移、读写、删除、损坏数据恢复及重启恢复测试；若未批准，明确每次启动为临时会话并在 UI 提示，不声称历史已保存。
4. 全面检查 i18n 键集一致、主题浅/深色适配、键盘提交与焦点、窄窗口布局、空/加载/错误/离线状态、图标语义和无障碍标签。用户可见文案不得硬编码，禁止 emoji。
5. README 说明功能边界、所需配置、数据如何处理、联网目的地/provider、会话是否持久化、权限理由、支持平台、内核兼容范围及已知限制；第三方 Pi 依赖、版本、许可证和随包内容同步至 `THIRD_PARTY_NOTICES.md`。

**验收**：目标平台完成完整手工验收；状态切换、重试、切换会话、取消和异常恢复正确；无敏感数据越界；文案、主题、图标和性能约定符合模块规范。

### 6. 测试、构建和官方模块列表提审

1. 每次变更先跑相关单测；完成时运行仓库可用的完整检查：

   ```powershell
   npm test
   npm run schema:check
   npm run build:frontend
   cargo test --manifest-path src-tauri/Cargo.toml
   npm run build:backend
   ```

2. 按发布流程运行打包与本地结构检查：

   ```powershell
   npm run package
   npm run check:release
   npm run submit
   ```

   以脚本实际参数和输出为准；若脚本要求 CI 环境或版本/tag 参数，按[发布流程](发布流程.md)执行，不通过手工修改输出绕过校验。
3. 审核 `module.json` 与 `.github/workflows/module-package.yml` 的平台矩阵一致：每个声明平台必须有真实构建产物；逐平台核对动态库扩展名、backend 文件主干、前端 `register.js`/assets、清单和图标。检查包内不含源码密钥、开发配置、未声明二进制或不必要文件。
4. 执行许可证与依赖供应链检查：Pi 直接依赖和传递依赖均有锁定版本、兼容许可及来源；第三方声明覆盖实际随包分发内容。发现许可不兼容时停止发布，不通过删 notice 处理。
5. 使用 CI 生成的 `.cglm` 与 `.sha256`，在干净用户数据环境逐平台验证下载校验、安装、重启加载、前端装配、凭证配置、问答、诊断工具、卸载和重装。官方列表提交 PR 后检查条目平台、权限、兼容版本、资产 URL 与校验值；由维护者审核合并。
6. 按维护者指令更新版本号、CHANGELOG/README 并发布；不得自行打 tag、覆盖已发布资产或提前宣称一键安装已可用。

**交付验收**：CI 构建、测试、包结构、逐平台安装验收全部通过；官方目录条目已进入审核流程；用户可通过官方列表实际完成安装并运行首期闭环。只完成源码、Release 资产或 cgl-libs PR 任一部分都不算交付完成。

## 备注

- 当前仓库 `package.json` 已有 `build:frontend`、`build:backend`、`package`、`submit`、`check:release`、`schema:check`、`test` 脚本；没有单独声明 lint/typecheck 脚本。不要在文档之外假定存在未配置的 npm 命令。
- CopperCore 源码可见附加模块动态库装载、通用模块调用、附加模块前端资源服务及安装命令；但模块发布文档仍记录一键安装和隔离能力尚未生效。实现前需用当前目标分支、启动器版本和真实包做端到端验证，并据结果协调更新文档；不以旧文档或单个符号推断整体状态。
- 现有模块框架是 Rust 动态库，Pi SDK 是 JavaScript/TypeScript 包。两者承载边界、可用 runtime、MCP 传输和安全凭证访问是本项目的关键风险门禁。若当前模块契约不能在不改 CopperCore 的情况下满足密钥保护和安装运行要求，应如实停止并报告差距，而不是把密钥放进 WebView 或自行发明内核 API。
- 本步骤仅覆盖 `cgl-agent` 的实现与发布准备。任何 CopperCore 所需变更均作为外部依赖单独提出，须经用户确认后另行安排。
